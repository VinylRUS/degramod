# Интеграция с Bothost Agent API — дизайн (v5.1.0)

**Дата:** 20 августа 2026
**Статус:** дизайн утверждён, реализация не начата
**Задачи роадмапа:** 5.0.0-02, -03, -04, -05, -06 (перенесены в v5.1.0)
**Базовая версия:** v5.0.0 (`b65d50d`)

---

## 1. Что разблокировалось

Пять пунктов Bot Self-Awareness ждали доступа к Bothost Agent API. Документация
получена 20.08.2026, переменные окружения на проде уже заданы владельцем:

| Переменная | Значение на проде | Смысл |
|---|---|---|
| `BOT_ID` | задан платформой | идентификатор контейнера |
| `USER_ID` | задан платформой | владелец бота |
| `BOTHOST_AGENT_URL` | не задан (используется дефолт) | адрес агента |
| `SELF_HEALING_ENABLED` | `0` | автоперезапуск выключен |
| `BOT_WEBHOOK_MODE` | `off` | автоопределение вебхука выключено |

Последние две созданы заранее с безопасными значениями: код приезжает целиком,
автоматика спит до осознанного включения.

## 2. Ограничение, определяющее весь подход

**Агент доступен только изнутри Docker-сети Bothost.** Проверено: локально
`agent:8000` не резолвится, `agent.bothost.ru:80` отказывает в соединении.
Значит:

- ни одну функцию нельзя проверить локально живым вызовом;
- тесты идут на моках HTTP-клиента, а не на реальном агенте;
- отсутствие агента — **штатное состояние**, а не авария. Панель обязана
  работать без него: блоки показывают «агент недоступен», кнопки неактивны,
  бот функционирует как раньше;
- документация датирована 2025 годом и может расходиться с реальностью,
  поэтому первым делом строится диагностика (§4).

## 3. Модуль доступа — `bothost_agent.py`

Один модуль в корне рядом с `health_probe.py`. Не тянет ни FastAPI, ни aiogram.

### 3.1. Определение адреса

Алгоритм из документации:

1. попытка TCP-соединения с `agent:8000` (таймаут 1 сек);
2. при неудаче — `BOTHOST_AGENT_URL`;
3. при отсутствии переменной — `None`, то есть «адреса нет».

**Проверено на проде 20.08.2026, документация в этой части неверна.**

- Внутренний `agent:8000` недоступен: имя не резолвится
  (`[Errno -2] Name or service not known`) — контейнер бота не в Docker-сети
  агента. Внутренний путь закрыт, полагаться на него нельзя.
- Внешний `agent.bothost.ru`, названный в документации, **не работает**:
  резолвится, но отказывает в соединении на 80, 443 и 8000. Проверка
  контролем: несуществующий поддомен отвечает тем же 404 с того же адреса,
  то есть отвечает wildcard-прокси, а не агент.
- Рабочая схема — **`http://<нода>.bothost.ru`** (`nl9`, `msk1`, …). Имя ноды
  видно в панели Bothost. Живой ответ:
  `GET /api/bots/{BOT_ID}/stats` → `401 {"ok":false,"msg":"Unauthorized: missing Bearer token"}`.

Публичного дефолта в коде намеренно нет: нода у каждой установки своя, а
угаданный адрес выглядел бы рабочим и превращал «адрес не настроен» в
«агент лежит» — ровно эта подмена и стоила нам нескольких итераций.

### 3.1.1. Авторизация

Пункт, потерянный при первом переносе документации, хотя
`roadmaps/ROADMAP_v5.0.0.md:651` его требует: агент авторизует запросы
заголовком `Authorization: Bearer <ключ>`. Без него — 401
`missing Bearer token`, с неверным значением — 401 `invalid token`.

Ключ берётся из первой заданной переменной списка `TOKEN_ENV_NAMES`:
`BOT_API_TOKEN`, `API_TOKEN`, `BOTHOST_API_TOKEN`, `AGENT_TOKEN`. Какая из
них содержит верный ключ, снаружи не видно, поэтому при ответе
`Unauthorized` блок диагностики перебирает заданные переменные и
показывает, какую агент принял. В панель уходят **имена** переменных;
значения ключей не выводятся никогда.

Результат кешируется в модульной переменной: дёргать socket на каждый запрос
незачем, а адрес в пределах жизни контейнера не меняется. Кеш сбрасывается
функцией `reset_cache()` — нужна тестам.

### 3.2. Контракт методов

Все методы возвращают `AgentResult` — датакласс с полями `ok: bool`,
`data: dict | None`, `error: str | None`. **Исключений наружу не бросают.**

Причина: вызовы идут из веб-роутов и фоновой задачи. Роут должен показать
«агент недоступен», а не отдать 500; фоновая задача, падающая от сетевого
сбоя, перестала бы работать ровно тогда, когда это нужнее всего.

| Метод | Endpoint | Назначение |
|---|---|---|
| `probe()` | `GET /api/bots/{BOT_ID}/stats` | диагностика: отвечает ли агент |
| `get_stats()` | `GET /api/bots/{BOT_ID}/stats` | CPU, память, uptime |
| `get_logs(lines)` | `POST /api/bots/logs` | последние N строк |
| `restart_self()` | `POST /api/bots/self/restart` | самоперезапуск |

Таймаут 10 секунд (как в примерах документации). HTTP-клиент — `aiohttp`,
он уже в зависимостях.

`restart_self` использует `/api/bots/self/restart` с заголовком `X-Bot-ID`, а
не общий `/api/bots/restart` с телом: документация называет его безопасным для
самоперезапуска, и он не требует передавать `user_id`.

### 3.3. Отсутствие `BOT_ID`

Локально переменной нет. Все методы при пустом `BOT_ID` сразу возвращают
`ok=False, error="BOT_ID не задан"` — без похода в сеть.

## 4. Диагностика — строится первой

Блок «Bothost Agent» в Settings показывает:

- выбранный URL и способ выбора (внутренний / из переменной / дефолт);
- отвечает ли агент;
- сырой ответ на `stats` — чтобы сверить формат с документацией.

Это единственный способ узнать, совпадает ли документация 2025 года с
реальностью. Владелец открывает страницу, смотрит ответ и присылает его —
дальше остальные функции пишутся под фактический формат.

Блок безопасен: только чтение, `require_su`.

## 5. Функции только для чтения

### 5.1. `-03` Логи контейнера

`POST /api/self/logs` в новом `web/self_admin.py`, под `require_csrf_su`
(POST — значит CSRF обязателен по инварианту проекта).

UI: окно ~350px, моно-шрифт, тёмный фон, автоскролл вниз. Кнопки «Обновить»,
«Автопрокрутка», «Очистить экран». Параметр `lines` по умолчанию 200.

### 5.2. `-04` Дашборд здоровья контейнера

`GET /api/self/stats`, под `require_su`. **Кеш 10 секунд** — иначе
автообновление раз в 30 секунд у нескольких открытых вкладок превратится в
поток запросов к агенту.

UI: CPU, память (прогресс-бар), uptime. При памяти выше 85% индикатор
краснеет; выше 95% — подсвечивается кнопка перезапуска.

Данные агента дополняют, а не заменяют `/healthz`: тот показывает процесс
изнутри (RSS, задержка Telegram), агент — контейнер снаружи (CPU, лимиты).

---

## 6. `-02` Ручной перезапуск

`POST /api/self/restart` под `require_csrf_su`. Кнопка в Settings с
подтверждением, как у «Backup now».

После нажатия — сообщение «перезапуск запущен» и опрос `/healthz` раз в 2
секунды до ответа. Если агент недоступен, кнопка неактивна с пояснением: не
даём нажать то, что заведомо не сработает.

Действие разрушительное, но запускается человеком осознанно и требует роли
`su` плюс CSRF-токен.

---

## 7. `-05` Self-healing — за флагом, выключен

**`SELF_HEALING_ENABLED=1` включает, любое другое значение — выключено.**
На проде стоит `0`.

Фоновая задача раз в 60 секунд, отдельная от пробника здоровья (у того свои
задержки, и подвисший вызов агента не должен мешать замерам Telegram).

**Условия перезапуска** (из роадмапа):

- память выше 90% лимита контейнера;
- Telegram недоступен дольше 5 минут.

**Ограничители:**

- не более 3 перезапусков за 10 минут; при исчерпании — стоп, алерт SU и
  больше никаких попыток до ручного вмешательства;
- если `memory_percent` неизвестен (`None` — лимит cgroup не найден), условие
  по памяти **не применяется вовсе**. Иначе на хосте без cgroup-лимита
  автоматика сходила бы с ума;
- перед перезапуском — проверка, что не выполняется операция модерации.

Каждый перезапуск сопровождается алертом SU с причиной: молчаливый рестарт
прода недопустим.

## 8. `-06` Авто-webhook — за флагом, `off` по умолчанию

**`BOT_WEBHOOK_MODE`:**

| Значение | Поведение |
|---|---|
| `off` (по умолчанию) | текущая логика: вебхук только если задан `WEBHOOK_URL` |
| `auto` | если `WEBHOOK_URL` пуст, собирается из `DOMAIN` |
| `force` | вебхук обязателен, при неудаче — ошибка старта |

На проде стоит `off`, то есть поведение не меняется.

Риск именно здесь самый неприятный: ошибка не роняет бота, а тихо лишает его
входящих сообщений — панель работает, логи чистые, а бот «молчит». Поэтому
режим `auto` при неудачной установке вебхука **откатывается на long polling**
и пишет об этом в лог, а не оставляет бота без обоих каналов.

## 9. Что проверяется тестами

Живого агента нет, поэтому HTTP-клиент мокается. Проверяется поведение, а не
переписка с сервером:

- выбор URL: внутренний доступен → берём его; недоступен → переменная;
  переменной нет → дефолт;
- пустой `BOT_ID` → отказ без похода в сеть;
- недоступный агент → `ok=False` с внятной причиной, исключение не всплывает;
- таймаут → то же самое;
- некорректный JSON в ответе → то же самое;
- роуты отдают понятное состояние без агента и требуют `su` (+CSRF на POST);
- кеш статистики: два запроса подряд дают один вызов агента;
- self-healing: выключен по умолчанию; ограничитель считает окно; при
  `memory_percent=None` не срабатывает; исчерпание лимита шлёт алерт;
- `BOT_WEBHOOK_MODE=off` не меняет текущую логику выбора канала.

## 11. Порядок работ

1. `bothost_agent.py` + тесты — фундамент, ни на что не влияет.
2. Диагностический блок — даёт факты о реальном агенте.
3. **Пауза: владелец смотрит блок и присылает фактический ответ.**
   Дальнейшие функции пишутся под реальный формат.
4. Логи и статистика (только чтение).
5. Кнопка перезапуска.
6. Self-healing за флагом.
7. Авто-webhook за флагом.
8. Документация, версия 5.1.0.

Шаг 3 — не формальность: если формат ответа расходится с документацией,
пункты 4–7 придётся переписывать, и лучше узнать это до, а не после.

## 12. Вне объёма

- Управление чужими ботами: API это позволяет (`/api/bots/restart` с любым
  `bot_id`), но документация прямо требует работать только со своим
  контейнером.
- `POST /api/bots/stop` и `/start`: остановленный бот не сможет сам себя
  запустить — кнопка «Stop» в панели превратила бы её в ловушку.
- Хранение истории статистики: агент отдаёт мгновенные значения, для графиков
  нужна отдельная таблица и политика хранения. Отдельная задача.
