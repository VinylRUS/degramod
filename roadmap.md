## 0. Описание бота (справка)

**Дедушка Вобжак** — Telegram-бот-модератор для чата Бабая. Бот + веб-панель
в одном контейнере. Хостится на **Bothost**.

**Архитектура (актуально после v4.8.x):**
- `bot.py` — точка входа, FastAPI + Aiogram.
- `bot_handlers.py` — обработка команд и сообщений.
- `web_app.py` (FastAPI) + Jinja2-шаблоны — веб-панель.
- `db.py` — SQLite, SQLAlchemy async.
- Модели: `User`, `Moderator`, `Punishment`, `ChatAdmin`, `ChatSettings`,
  `PermissionPreset`, `WebUser`, `KeywordWatch`, `LinkAllowlist`,
  `BannedStickerPack`, `Base` (без `WordFilter` после v4.8.1).
- Модули v4.8.x: `chat_modes.py`, `modchat.py`, `sticker_cache.py`.
  `backup.py` (B2-бэкапы) — отложен в v5.0.0.

**Стек:** Python 3.11+, aiogram 3.x, FastAPI, SQLAlchemy 2.x (async), Jinja2.
**Хостинг:** Bothost (Docker-контейнер, agent API на `http://agent:8000`).
**Версионирование:** `v{MAJOR}.{MINOR}.{PATCH}`.

## 2. ⚠️ Архитектурные инварианты — не нарушать никогда

Общие для всех версий, перенесены без изменений из `ROADMAP_v4.8.0.md`.

1. **Alarm / Night mode / Sanitary day работают с chat-default permissions,
   НЕ с per-user overrides.**
   `bot.set_chat_permissions(...)` меняет только общие права чата.
   Индивидуальные рестрикты через `restrict_chat_member(user_id=...)`
   хранятся отдельно и не снимаются автоматически.
   - `!alarm on` — «только текст» на весь чат; персонально замьюченный
     юзер остаётся замьюченным (min(chat, user)).
   - `!alarm off` — восстанавливает chat-default права, персональные
     рестрикты не трогает.
   - Нельзя вызывать `restrict_chat_member` для всех при входе/выходе из alarm.
   - Нельзя снимать per-user мьюты при `!alarm off`.

2. **Snapshot прав берётся из `chat.permissions`**, не из individual members
   (`bot.get_chat(chat_id).permissions`).

3. **`use_independent_chat_permissions=True`** — обязателен для всех
   `set_chat_permissions`. С v4.7.25, централизован в `_apply_chat_permissions`
   (`chat_modes.py`). Никогда не убирать.

4. **Snapshot хранится в JSON**, не в объекте `ChatPermissions`.
   Поля: `alarm_saved_permissions`, `night_mode_saved_permissions`,
   `sanitary_days_saved_permissions` — JSON-строка с 13 полями `_PERM_FIELDS`,
   десериализация через `_restore_permissions()`.

5. **Порядок tick'ов: alarm → sanitary → night.** В `_night_mode_loop` и
   `_startup_recovery`. Менять нельзя — иначе санитарный день может войти
   до alarm'а и сделать snapshot alarm-состояния.

6. **`_deactivate_alarm` возвращает tuple `(ok, perms_source, slow_source)`**
   (с v4.7.30). Старый код `if await _deactivate_alarm(...)` работает
   (tuple truthy при ok=True), но лучше явно распаковывать.

## 3. v4.8.1 — Стабилизация + реформа команд + web unban ✅

**Релиз:** 8 августа 2026.

### 3.1. Реформа команд ban/warn/mute

**Проблема (v4.8.0):** `!ban` требовал причину, но не регистрировался без неё;
команды были слишком «тихими» — ни нарушитель, ни чат не видели публичной реакции.

**Решение:** разделение на «громкие» (публичные, причина обязательна) и
«тихие» (стелс, причина опциональна) команды.

| Команда | Тип | Причина | Публичное сообщение | Ephemeral модератору | Ephemeral нарушителю |
|---|---|---|---|---|---|
| `!ban` | громкая | обязательна | ✅ | ❌ | — |
| `!warn` | громкая | обязательна | ✅ | ❌ | ❌ |
| `!mute` | громкая | обязательна | ✅ | ❌ | — |
| `!sban` | тихая | опциональна | ❌ | ✅ | — |
| `!swarn` | тихая | опциональна | ❌ | ✅ | ✅ (исключение) |
| `!smute` | тихая | опциональна | ❌ | ✅ | — |

Форматы публичных сообщений:
- `!ban`: `Пользователь "X" забанен за "причина"`
- `!warn`: `Пользователь "X" получил варн за "причина"`
- `!mute`: `Пользователь "X" замутан за "причина" на "N"`
- Via-фильтр (авто-мьют): фиксированный текст без причины.

Пересланное сообщение к публичному тексту **не** прикладывается (только в
репорт-чате). Отчёт в репорт-чат падает всегда — и для громких, и для тихих
команд. Новый хелпер `_send_public_punishment_notice(...)`.

Не изменилось: `!unban/!unmute/!unwarn/!warns/!resetwarns`, авто-санкции по
порогам warn→mute→ban, CAS/link-filter бан, keyword-watch.

**Файлы:** `bot_handlers.py`, `templates/base.html`,
`scripts/test_v481_command_reform.py`. **Оценка:** ~1.5 дня.

### 3.2. Удаление deprecated word_filter

Удалить из кода использование модели `WordFilter`, `handle_word_filter` и
связанные функции; таблицу в БД оставить для истории. **Оценка:** ~0.5 дня.

### 3.3. Web unban — новая вкладка «Active bans» (#3)

Страница `/admin/bans`: таблица активных банов (время/юзер/чат/модератор/
причина/кнопка Unban), фильтры и сортировка, pagination. Кнопка Unban →
confirm dialog → `POST /api/unban` → soft-revoke Punishment + Telegram
`unban_chat_member` + новая запись Punishment(action_type='unban').
Batch-unban и авто-уведомление юзера — не делаем.

**Файлы:** `web_app.py`, `templates/admin_bans.html` (NEW), `bot_handlers.py`
(вынос логики `!unban` в переиспользуемую функцию), `db.py`,
`scripts/test_v481_web_unban.py`. **Оценка:** ~2 дня.

### 3.4. Ослабление version-mismatch тестов

`test_v454_sanitary_day.py`, `test_v460_granular_perms.py`:
`assertEqual` → `assertGreaterEqual` по версии. **Оценка:** ~0.2 дня.

## 5. v4.8.3 — Бан по @username/TGID + стикер/скриншот inline ✅

**Релиз:** 11 августа 2026. Подтверждено в проде: скриншоты работают на
всех 6 командах, TGS fallback OK, поведенческих багов не найдено.

### 5.1. Три способа указать цель наказания

Для всех 6 команд (`!ban/!sban/!warn/!swarn/!mute/!smute`):
1. **Reply** (как раньше) — приоритетнее всего.
2. **@username** — сначала `MessageEntityTextMention`, потом поиск в БД
   `User.username`; не найден → ephemeral с ошибкой.
3. **TGID** — парсинг int + `get_chat_member()`.

Новый хелпер `_resolve_punishment_target(message, target_str)`.

### 5.2. Стикер inline в Details-блоке отчёта

Вместо отдельного `send_sticker` — стикер встраивается в Details-блок
«📎 Сообщение юзера»:
- Static (`.webp`) → Pillow → PNG → `InputRichBlockPhoto`.
- Video (`.webm`) → `InputRichBlockAnimation`.
- Animated (`.tgs`) → `rlottie-python` → PNG; при ошибке — fallback на
  отдельный `send_sticker`, как раньше.

Всё через `BytesIO`, на диск ничего не пишется.

### 5.3. Скриншот от модератора

Если команда написана в caption к фото — фото парсится, кладётся в
отдельный Details «📷 Скриншот от модератора» (закрыт по умолчанию).

### 5.4. Стикерпак-нотификация

При новом добавлении стикерпака в `BannedStickerPack` — пункт в List
«📦 Использованный стикерпак забанен: name».

**Файлы:** `bot_handlers.py`, `sticker_cache.py` (NEW),

## 6. v4.8.4 — Прогрессивные автомьюты ✅

**Релиз:** 13 августа 2026.

**Формула:** `mute_duration = base_duration + (automute_count × 60 сек)`,
где `automute_count` — значение счётчика ДО инкремента (0 при первом мьюте).

| # мута | count до | duration | count после |
|---|---|---|---|
| 1-й | 0 | 5м | 1 |
| 2-й | 1 | 6м | 2 |
| 11-й | 10 | 15м | 11 |

**Реализация:**
- Новая таблица `automute_counters` (PK `chat_id+user_id`, `count`, `updated_at`).
- Хелперы `_get_automute_count`, `_increment_automute_count`, `_reset_automute_count`.
- Затронуты 4 пути автомьюта: порог варнов, via-bot фильтр, стикерпак-фильтр,
  контент/линк-фильтр. Ручные `!mute/!smute` — не затронуты, счётчик не растёт.
- Новая команда `!resetmc` (SU/Admin) — сброс счётчика, reply/@username/TGID.
- Веб-эндпоинт `POST /api/reset-automute-count`.
- Счётчик НЕ сбрасывается ни при `!resetwarns`, ни при `!unmute`; растёт
  бесконечно, кэпа и автобана после N мутов нет; счётчик per-chat.

**Файлы:** `db.py` (модель `AutomuteCounter`), `bot_handlers.py`, `web_app.py`,
`templates/base.html`, `scripts/test_v484_progressive_automutes.py`.
**Оценка:** ~1 день.

## 7. v4.8.5 — `!idea` → GitHub Issue + GitHub Project 📋

**Статус:** запланировано, ещё не реализовано.

**Цель:** дать модераторам/админам канал предложений — команда
`!idea <текст>` в ЛС боту или в модчате → автоматический GitHub Issue
+ добавление в GitHub Project (колонка «Предложено»). Настройка подключения
— через веб-панель, без ручной правки env.

**Ключевые решения:**
- Каналы: только DM и modchat (в обычных чатах команда недоступна).
- В GitHub уходит только заголовок Issue = текст идеи (без body). Метаданные
  (автор, дата, источник, версия бота) — только в БД, таблица `idea_log`.
- Лимит — 200 символов, иначе отказ.
- Без cooldown, без модерации — идея уходит в GitHub сразу.
- Ответ отправителю: «Спасибо за идею. Передал.» + алерт SU в DM со ссылкой
  на Issue. При ошибке — алерт SU с текстом ошибки и идеи (чтобы не потерять).
- Доступ: SU/admin/moderator. Обычные юзеры — молчаливый игнор.
- **Не делаем в этой версии:** голосование/лайки, авто-перенос между
  колонками проекта, привязку к commit/PR, категории/теги.

**Настройка через веб-панель (Settings → GitHub Projects):**
PAT (шифруется в БД), repo owner, repo name, Project node ID, Project number,
кнопка «Проверить» (test connection — создаёт и сразу закрывает тестовый Issue).

**Таблица `idea_log`:** `id, tg_user_id, tg_username, source(dm/modchat),
idea_text, github_issue_url, github_issue_number, created_at, bot_version`.

**Файлы:** `bot_handlers.py` (обработчик `!idea`), `web_app.py`
(`GET/POST /admin/settings/github`, `POST /admin/settings/github/test`),
`db.py` (`idea_log`, `github_settings`), `templates/base.html`,
`templates/admin_settings.html` (или новый `admin_github.html`),
`requirements.txt` (+httpx/aiohttp, +cryptography).

**Оценка:** ~1.5 дня (0.5 обработчик+API, 0.5 веб-панель+шифрование,
0.5 БД+тесты+edge-cases).

### 9.2. §2 — Запросы модераторов

**2.1. Самопроверка варнов обычными юзерами** (запрос @Gleb, 11 августа 2026,
через бустерский чат) — единственный уже зафиксированный запрос, остальные
ждут совещания.

- **Проблема:** сейчас `!warns` доступен только модераторам (reply-only,
  guard `_is_admin`), результат уходит модератору в DM. Юзеры регулярно
  спрашивают у модераторов «сколько у меня варнов» — лишний шум.
- **Показываем юзеру:** текущее число активных варнов + пороги автомьюта/
  автобана. **Не показываем:** причины варнов, кто выдал, timestamps.
- **Дизайн (предложение, рекомендация — `/mywarns`):**
  - DM без аргументов — сводка по всем чатам одной строкой на чат.
  - DM с `<chat_id>` — детальный отчёт по чату.
  - В группе — команда удаляется (privacy), бот шлёт DM; если DM
    недоступен — ephemeral с auto-delete через 30 сек.
- **Edge cases:** нет варнов в этом чате, но есть в других; учёт
  `warn_decay_days`; чат без `ChatSettings` → дефолтные пороги; юзер уже
  забанен/замучен — варны всё равно показываем.
- **Что нужно подтвердить у пользователя:** синтаксис (`/mywarns` vs
  `!mywarns`), формат вывода (краткий/verbose), поведение в группе
  (удалять команду? слать DM? ephemeral-fallback?).

**Файлы:** `bot_handlers.py` (regex `_CMD_MYWARNS`, handler `cmd_mywarns`,
хелперы `_format_user_warns_summary`/`_format_user_warns_for_chat`),
help-тексты, `templates/base.html`, `scripts/test_v490_mywarns.py`.

**Оценка:** ~1 день. **Приоритет:** высокий (простой запрос, частая боль

### 10.2. Детали по задачам

**5.0.0-01 — Блок «Информация о боте».** Показать из env (`BOT_ID`, `DOMAIN`,
`TEMPLATE`, `USER_ID`, `PORT`), из рантайма (`APP_VERSION`, `HOSTNAME`), из
файловой системы (`/app/data` есть? `/.dockerenv` есть?). Статус-бейдж:
🟢 активен / 🟡 проблемы с TG API / 🔴 перезапуск.
Файлы: `web_app.py` (`GET /api/self-info`), `templates/settings.html`,
`static/css/settings.css`.

**5.0.0-02 — Кнопка «Перезапустить».** `POST /api/self/restart` →
Bothost Agent `POST /api/bots/self/restart` с `X-Bot-ID`. После клика —
toast + poll `/api/self-info` каждые 2 сек до ответа. Fallback: если
`agent:8000` недоступен — кнопка disabled с тултипом.
Новый модуль `bot/bothost_agent.py` (обёртка над Agent API, переиспользуется
в 03/04/05).

**5.0.0-03 — Окно логов.** Окно ~350px, моно-шрифт, тёмный фон, автоскролл.
`POST /api/self/logs?lines=200` → Agent `POST /api/bots/logs`. Кнопки
«Обновить»/«Автопрокрутка»/«Очистить экран», опционально фильтр по regex.

**5.0.0-04 — Дашборд здоровья.** `GET /api/bots/{BOT_ID}/stats`: CPU
(круговой индикатор), memory (прогресс-бар), uptime. Обновление раз в 30 сек.
При `memory_percent > 85` — индикатор краснеет с подсказкой; при `> 95` —
кнопка «Перезапустить» подсвечивается пульсацией. Прокси-роут с кэшем 10 сек.

**5.0.0-05 — Self-healing.** Фоновая asyncio-таска, проверка раз в 60 сек:
`memory_percent > 90` → рестарт (`high_memory`); 3+ `MemoryError` за 5 мин →
рестарт (`memory_error`); TG API не отвечает 5 мин → рестарт
(`tg_api_unreachable`). Защита от цикла: не более 3 рестартов за 10 минут,
иначе бот останавливается и шлёт SU алерт о ручном вмешательстве.
Риски: может оборвать активные команды (проверка `active_tasks_count` перед
рестартом, отсрочка 30 сек); конфликт с ручным рестартом — мьютекс
`restart_in_progress`.

**5.0.0-06 — Авто-webhook из `DOMAIN`.** Флаг `BOT_WEBHOOK_MODE`: `off`
(дефолт в v5.0.0, ничего не меняется) / `auto` (читает `DOMAIN`) / `force`
(всегда webhook, требует `WEBHOOK_URL`). ⚠️ Риск сломать текущий long
polling — включать только явно.

**5.0.0-07 — `/healthz`.** Публичный, не требует БД/TG/авторизации.
JSON: `status(ok/degraded/down)`, `bot_id`, `container_id`, `version`,
`uptime_seconds`, `memory_mb`, `memory_percent`, `telegram_connected`,
`telegram_api_latency_ms`, `timestamp`. `degraded` при memory>85% или TG
недоступен/латентность>1000ms; `down` при memory>95%. HTTP 200/503.
Ценность: обнаружение деградации за 30+ минут до краша (memory leak,
торможение TG API) — работает даже когда основной цикл бота упал.

**5.0.0-08 — Алерт SU при задержках TG API.** Обёртка над ключевыми
вызовами Bot API с замером времени, `deque(maxlen=10)` последних latency.
5 подряд запросов > 1000ms → алерт SU в DM с деталями (антиспам: не чаще
раза в 30 минут). Поле `telegram_api_latency_ms` добавляется в `/healthz` и
в виджет здоровья.

`get_logs(lines)`, `close()`. Используется в задачах 02/03/04/05.
(Полный код-скелет — в исходном `Roadmap_5_0_0.md`.)
