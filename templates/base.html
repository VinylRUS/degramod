v4.8.1 — 8 августа 2026 (патч: реформа команд ban/warn/mute + web unban + удаление word_filter)

  • Реформа команд ban/warn/mute. Громкие команды !ban/!warn/!mute теперь публикуют короткое публичное сообщение в чат (Пользователь "X" забанен за "Y"), без ephemeral модератору. Причина для громких — обязательна. Добавлены тихие команды !sban/!swarn/!smute (stealth-режим) — копия v4.8.0 поведения с ephemeral модератору. Причина для тихих — необязательна. Для !swarn сохранено ephemeral-уведомление нарушителю (особое требование). Ephemeral про автодобавление стикерпака при бане за стикер — остаётся для !ban и !sban.
  • Via-фильтр: публичное сообщение. При срабатывании via-bot rate-limit фильтра бот теперь публикует в чат Пользователь "X" задолбал срать в чат и был замутан на "Y" (фиксированный текст, без причины — она техническая).
  • Удаление deprecated word_filter. Код WordFilter объявлен deprecated в v4.8.0 (заменён на KeywordWatch). В v4.8.1 код word_filter полностью удалён из bot_handlers.py (функция _word_filter_match, обработчики /addword//delword//listwords отвечают заглушкой с подсказкой перейти на !addkeyword/!delkeyword/!listkeywords). Модель WordFilter оставлена в db.py для сохранения таблицы в БД (исторические данные). Таблица word_filters НЕ удаляется.
  • Web unban (#3). Новая страница /admin/bans — таблица всех активных банов по всем чатам, с фильтрами по chat_id и поиску по юзеру. Кнопка Unban в каждой строке: soft-revoke исходной записи + вызов Telegram API unban_chat_member + новая запись action_type='unban' с указанием модератора и причины (опциональной). Доступ: все аутентифицированные веб-юзеры. Полный паритет с TG-командой !unban — обе используют переиспользуемую функцию revoke_user_ban в bot_handlers.py.
  • Переиспользуемая функция revoke_user_ban. Логика разбана вынесена из inline-обработчика !unban в отдельную функцию — используется и TG-командой, и веб-API. Делает: unban_chat_member + _revoke_last_action (помечает последний активный бан как снятый) + _save_punishment с action_type='unban'.

v4.8.0 — 8 августа 2026 (major-update: рефакторинг режимов + modchat + keyword-watch + веб-UI)

  • Major-update v4.8.0: реализованы 3 задачи из ROADMAP_v4.8.0.md — #4 (аудит кода), #9 (рефакторинг системы режимов), #10 (modchat + keyword-watch).
  • #4: Аудит кода. Проведён полный аудит кодовой базы (4 Python-модуля + 9 HTML-шаблонов + 39 тестов). Отчёт сохранён в CODE_AUDIT_v4.8.0.md. Найдено: 0 критических проблем, несколько зон для улучшения. Главный риск — дублирование snapshot/restore логики между alarm/night/sanitary режимами (устранено в #9).
  • #9: Рефакторинг системы режимов. Создан новый модуль chat_modes.py с унифицированной логикой:
    • _snapshot_chat_permissions(bot, chat_id, day_permissions=None) — единая функция snapshot для всех трёх режимов (alarm/night/sanitary).
    • _resolve_restore_perms_async(session, cs, saved_permissions_field, saved_source_name) — единая логика выбора прав для восстановления (4-уровневый fallback: day_permissions preset → system Day default → snapshot режима → hardcoded default).
    • _apply_chat_permissions(bot, chat_id, perms) — обёртка над set_chat_permissions с обязательным use_independent_chat_permissions=True.
    • _mode_priority(cs) и _active_modes(cs) — хелперы для логирования (приоритет: sanitary > night > alarm > day).
    Дубликат логики snapshot'а удалён из _enter_night_mode, _enter_sanitary_day, handle_alarm_command. Дубликат логики restore удалён из _deactivate_alarm и _restore_day_state. Все 5 вызовов set_chat_permissions теперь идут через _apply_chat_permissions. Архитектурные инварианты (per-user overrides, snapshot из chat.permissions, independent mode, JSON snapshot, порядок tick'ов) сохранены и задокументированы в коде.
  • #10: Модераторский чат (modchat). Новый отдельный чат для оперативных оповещений модераторам. В отличие от report_chat (журнал санкций с rich-превью), modchat — краткий текстовый формат для быстрых оповещений. Взаимоисключение: один чат не может быть одновременно report_chat и modchat. Команда !setmodchat <chat_id> (SU-only, 0 = сбросить). Если modchat не задан — все оповещения молча пропускаются (DM модератору остаётся как раньше).
  • #10: Alarm-события в modchat. Все 4 события !alarm отправляются в modchat:
    • on — «🚨 В чате «X» поставлен режим тревоги модератором «Y». Длительность: N мин (до HH:MM МСК)».
    • off (ручное снятие) — «✅ В чате «X» снят режим тревоги модератором «Y»».
    • auto_off — «⏱ В чате «X» автоматически снят режим тревоги. Причина: истёк таймаут (проработал N мин)».
    • off_by_mode — «🔒 В чате «X» снят режим тревоги. Причина: вход в night mode / sanitary day».
    • extend (продление) — консолидация: если за 60 секунд было несколько продлений, шлём одно консолидированное сообщение с историей «кто, когда, на сколько». On/off/auto_off/off_by_mode — всегда мгновенно, без консолидации.
  • #10: Keyword-watch (замена word_filter). Новый механизм отслеживания фраз в сообщениях. Принципиально отличается от word_filter:
    • День: только notify в modchat (не банит, не удаляет, не варнит).
    • Ночь (active night mode): фразы с флагом ban_in_night_mode=True → автобан. Без флага → notify.
    • Match logic: фраза с пробелом → case-insensitive substring (фраза «срал в торт детишкам» найдёт только эту последовательность). Одиночное слово → word-boundary match (Unicode-aware, не сработает на «замодераторили» если в списке «модератор»).
    • Антиспам modchat'а: rate-limit 60 сек/фраза + multiplexing (3 совпадения в одном сообщении → 1 notify) + exempt модераторов/админов/SU через _is_admin().
    • Формат notify: HTML с упоминанием юзера (кликабельно → tg://user), временем МСК, списком совпадений, превью текста (до 500 символов), и кнопкой «Перейти к сообщению →» через message.link.
    • Управление: команды !setkeywords word1,word2,"фраза" [--ban-night] (полная замена), !addkeyword "фраза" [--ban-night], !delkeyword "фраза", !listkeywords (все SU-only). Также доступно через веб-панель: страница /admin/keywords (SU-only) — таблица активных фраз с чекбоксом «банить в night mode», формой добавления и кнопками удаления/переключения флага. Назначение modchat — кнопка ☆ MOD в карточке чата на странице /admin/chats (с взаимоисключением: один чат не может быть одновременно report_chat и modchat).
    • Хранение: новая таблица keyword_watch в БД. Глобальный список (chat_id=0 всегда — правила везде одни). Поля: phrase, ban_in_night_mode, rules_section (для будущего GitHub sync #11).
    • Миграция: ручная. Старый word_filter список НЕ переносится автоматически (он и так был пуст — боялись ложных срабатываний). Старый код word_filter оставлен для обратной совместимости, но объявлен deprecated. Удаление планируется в v4.8.1.
  • Новые поля БД: ChatSettings.mod_chat_id, ChatSettings.is_mod_chat. Новая таблица keyword_watch с индексами. Все миграции идемпотентны (PRAGMA check + ALTER TABLE / CREATE TABLE IF NOT EXISTS).
  • Новые модули: chat_modes.py (210 строк, унифицированная логика режимов), modchat.py (370 строк, modchat + keyword-watch).
  • Регрессия: все 288 тестов v4.7.x проходят. Ослаблены 2 теста v4.7.25 (проверяли прямые вызовы set_chat_permissions в bot.py — после рефакторинга вызовы ушли в chat_modes.py через _apply_chat_permissions, тесты обновлены для проверки ИЛИ прямого вызова с independent=True, ИЛИ вызова через _apply_chat_permissions).

v4.7.30 — 8 августа 2026 (audit fixes: !alarm + filters + CAS)

  • Аудит: проведён полный аудит команды !alarm on/off и других команд бота. Отчёт сохранён в AUDIT_v4.7.30_alarm_and_other_commands.md. Найдено 8 багов (2 критичных, 2 серьёзных, 4 минорных). В этом релизе исправлены 7 из 8 (минор #6 — оптимизация сессий БД — отложен до major-update v4.8.0).
  • Баг #1 (критичный): авто-выключение !alarm работало только для чатов с включённым ночным режимом. Логика auto-off была встроена в _night_mode_tick, который итерирует только чаты с night_mode_enabled=True. Чаты без ночного режима (нормальный сценарий — !alarm как замена ночному режиму) вообще не проверялись — alarm зависал навсегда даже при указанной длительности. Фикс: логика auto-off вынесена в отдельную функцию _alarm_auto_off_tick(), которая делает свой SQL query по всем чатам с alarm_currently_active=True и alarm_active_until IS NOT NULL. Функция вызывается первой в _night_mode_loop (перед sanitary/night tick'ами) и в _startup_recovery.
  • Баг #2 (критичный): после рестарта бота !alarm «зависал». В _startup_recovery (функция которая при старте проверяет чаты с зависшими active-флагами) alarm_currently_active отсутствовал в SQL query — только night_mode_currently_active и sanitary_days_currently_active. После краша/перезапуска alarm оставался активным навсегда, даже если alarm_active_until уже истёк. Фикс: alarm_currently_active.is_(True) добавлен в or_() query. Логирование расширено: теперь выводит alarm_active, alarm_until, alarm_started_by для каждого зависшего чата. Tick'и вызываются в правильном порядке: alarm → sanitary → night.
  • Баг #3 (серьёзный): санитарный день ломал snapshot прав alarm'а. _enter_sanitary_day делал snapshot текущих прав чата — но если в этот момент был активен alarm, snapshot содержал alarm-состояние (text-only) вместо настоящих дневных прав. При выходе из sanitary day чат восстанавливался в text-only, а поля alarm в БД оставались set. Фикс: _enter_sanitary_day теперь сначала деактивирует alarm через _deactivate_alarm(reason="sanitary_day_enter") — аналогично логике перед входом в night mode. Блок деактивации идёт ДО snapshot'а прав, чтобы snapshot содержал настоящие day-права.
  • Баг #4 (серьёзный): sticker/content filters наказывали самих модераторов. handle_sticker_message (бан стикерпаков) и handle_content_filters (word/link фильтры) не имели exempt'а для модераторов. Модератор, тестирующий фильтр запрещённым словом/ссылкой/стикером, мог быть забанен/замьючен собственным ботом. !mute/!warn/!ban имели explicit friendly-fire защиту, а для авто-фильтров её забыли. Фикс: оба handler'а теперь проверяют _is_admin(target.id, chat_id) ПЕРЕД удалением сообщения и наказанием. Если юзер — модератор, сообщение НЕ удаляется (чтобы модератор видел что оно дошло), наказание НЕ применяется, логируется INFO. Проверка fail-open: если БД лежит — лучше наказать, чем пропустить (для content/sticker filters); для CAS — наоборот, fail-open в пользу модератора (лучше пропустить, чем забанить своего).
  • Баг #5: !alarm off врал в личке. DM всегда писал «права восстановлены из сохранённого snapshot», но реально права могли восстановиться из day_permissions preset (если задан) — это приоритетный источник. Фикс: _deactivate_alarm теперь возвращает tuple (ok, perms_source, slow_source) вместо просто bool. Добавлены функции _alarm_perms_source_to_human() и _alarm_slow_source_to_human() — переводят технические source-строки в человекочитаемые описания («из day_permissions пресета чата», «из сохранённого snapshot», «из системного дефолта»). DM теперь пишет правду: «Права восстановлены: {perms_desc} • Slow mode: {slow_desc}».
  • Баг #7: !alarm on не сообщал, кто включил alarm до тебя. Если модератор А включил !alarm on 1ч, а потом модератор Б пишет !alarm on 2ч (продлить) — Б получал «Alarm уже был активен — продлён до 2ч», но не знал, что alarm включил А. В логах prev_started_by был, но в DM не попадал. Фикс: в ветке продления alarm теперь загружается профиль модератора из БД (Moderator.tg_user_id == old_started_by) и собирается строка «Имя @username id:NNN». DM теперь содержит «Предыдущий alarm включил: {prev_mod_display}». Best-effort: если профиль не найден — fallback на id:NNN.
  • CAS: модераторы/админы в игнор-листе. handle_new_members (CAS-проверка новых юзеров) теперь проверяет _is_admin(member.id, chat_id) перед CAS-запросом. Сценарий: модератор был ранее замечен в CAS-базе (в других чатах, давно), но в нашем чате он теперь полноценный модератор через ChatAdmin или ADMIN_IDS. Без exempt бот его забанил бы при входе в чат. Проверка fail-open: при ошибке БД — пропускаем юзера (лучше пропустить потенциального спамера, чем забанить своего модератора).
  • Баг #8 (документация): per-user overrides не задокументированы. Alarm / night mode / sanitary day работают с chat-default permissions, не с per-user overrides (индивидуальными рестрикты через restrict_chat_member). Если модератор персонально замьютил кого-то через !mute, этот мьют переживёт alarm/night/sanitary — правильно и должно быть. Но это поведение нигде явно не задокументировано, что могло привести к случайной поломке при рефакторинге. Фикс: в начало ROADMAP_v4.8.0.md добавлен раздел «⚠️ АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ — НЕ НАРУШАТЬ» с 6 правилами (per-user overrides, snapshot из chat.permissions, use_independent_chat_permissions=True обязателен, snapshot в JSON, порядок tick'ов, сигнатура _deactivate_alarm).
  • +45 новых регрессионных тестов в scripts/test_v4730_alarm_audit_fixes.py: Bug#1 (alarm auto-off для всех чатов), Bug#2 (alarm в startup_recovery), Bug#3 (sanitary снимает alarm), Bug#4 (filters exempt модераторов), Bug#5 (tuple return + DM truthfulness), Bug#7 (prev_mod_display), CAS exempt, ROADMAP invariants, no-regressions. Все 45 тестов проходят + все предыдущие 13 тест-сьютов regression OK.
  • Предложение по рефакторингу на v4.8.0: в ROADMAP_v4.8.0.md добавлена идея #9 — «Причесать систему режимов чата (alarm/night/sanitary)». Предлагается единый ChatModeManager класс-оркестратор, унифицированный snapshot, явная приоритизация режимов (sanitary > night > alarm > day). Решение — после v4.7.30 релиза, если багов не найдут.

Snapshot лежит в night_mode_saved_permissions / sanitary_days_saved_permissions в БД, так что recovery всегда возможен.
  • asyncio.Semaphore(100) для ephemeral auto-delete: каждое ephemeral-сообщение (уведомление модератору, варн-уведомление нарушителю, fallback-ответ в чат) порождает fire-and-forget корутину sleep(N) → delete_message. Раньше таких корутин создавалось без ограничений — поток из 1000 варнов за минуту породил бы 1000 спящих задач. Теперь Semaphore(100) ограничивает количество одновременно ожидающих auto-delete-задач: 101-я ждёт освобождения слота.
  • Hard shutdown timeout 5 секунд: если background task игнорирует CancelledError и не успевает завершиться за 5 секунд — бот логирует список всё ещё работающих задач и выходит принудительно. Event loop закроется, задачи умрут.
