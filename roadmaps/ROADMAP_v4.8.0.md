## ⚠️ АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ — НЕ НАРУШАТЬ

Эти правила описывают поведение, которое СУЩЕСТВУЕТ и КОРРЕКТНО работает.
При любом рефакторинге (особенно в major-update v4.8.0) — НЕ СЛОМАЙ их случайно.
Если меняешь логику night mode / sanitary day / alarm / restrict_chat_member —
сверься с этим списком.

### 1. Alarm / Night mode / Sanitary day работают с chat-default permissions, НЕ с per-user overrides

**Что это значит:** `bot.set_chat_permissions(...)` меняет только **общие права
чата** (default permissions для всех участников). Индивидуальные рестрикты,
выданные через `bot.restrict_chat_member(user_id=...)`, Telegram хранит ОТДЕЛЬНО
и `set_chat_permissions` их НЕ снимает и НЕ меняет.

**Почему это важно:**
- Alarm (`!alarm on`) ставит "только текст" на ВЕСЬ чат. Юзер, который был
  персонально замьючен раньше, ОСТАЁТСЯ замьюченным (его права = min(chat, user)).
- `!alarm off` восстанавливает chat-default права из snapshot/preset. Персональные
  рестрикты при этом НЕ трогаются. Это правильно — если модератор замьютил кого-то
  персонально через `!mute`, этот мьют должен пережить alarm.
- То же самое для night mode / sanitary day — они работают с chat-default,
  не с per-user.

**Если решишь "причесать" логику:**
- НЕ вызывай `restrict_chat_member` для всех юзеров чата при входе/выходе из
  alarm — это будет O(N) Telegram API вызовов и сломает per-user overrides.
- НЕ снимай per-user мьюты при `!alarm off` — модератор их выдал намеренно.
- Если появится фича "снять ВСЕ индивидуальные рестрикты в чате" — это должен
  быть ОТДЕЛЬНЫЙ механизм (например, `/resetrestrictions chat_id`), не часть alarm.

### 2. Snapshot прав в alarm/night/sanitary берётся из `chat.permissions`, не из individual members

`bot.get_chat(chat_id).permissions` возвращает chat-default права. Это то, что
нужно для snapshot'а — мы хотим восстановить chat-default, а не индивидуальные
рестрикты (которые не наши и не должны нами трогаться).

### 3. use_independent_chat_permissions=True — обязательно для всех set_chat_permissions

С v4.7.25 все вызовы `set_chat_permissions` в коде используют
`use_independent_chat_permissions=True`. Это отключает legacy-режим Telegram,
где `can_send_other_messages=True` неявно подтягивала `can_send_video_notes=True`
и другие поля через правило импликации. Без independent-режима пресеты ломаются.
**Никогда не убирай этот параметр** без полного ретеста всех сценариев
night/sanitary/alarm/mute.

### 4. Snapshot хранится в JSON, не в ChatPermissions объекте

`alarm_saved_permissions`, `night_mode_saved_permissions`,
`sanitary_days_saved_permissions` — все хранят JSON-строку с 13 полями из
`_PERM_FIELDS`. Десериализация через `_restore_permissions()`. Это нужно, чтобы
snapshot переживал рестарт бота (объект ChatPermissions в памяти потерялся бы).

### 5. Порядок tick'ов: alarm → sanitary → night

В `_night_mode_loop` (и в `_startup_recovery`) tick'и вызываются в строгом
порядке:
1. `_alarm_auto_off_tick()` — снимает alarm'ы с истёкшим `alarm_active_until`
2. `_sanitary_day_tick()` — входит/выходит из sanitary day
3. `_night_mode_tick()` — входит/выходит из night mode

Если изменить порядок — санитарный день может войти до того, как alarm снят, и
сделает snapshot alarm-состояния (Баг #3 аудита v4.7.30). И наоборот — night
mode может войти до alarm и сломать snapshot.

### 6. _deactivate_alarm возвращает tuple (ok, perms_source, slow_source)

С v4.7.30 сигнатура изменена. Если вызываешь `_deactivate_alarm(...)` — ожидай
tuple, не bool. Старый код, который делал `if await _deactivate_alarm(...)`,
всё ещё работает (tuple truthy если ok=True), но лучше явно распаковывать.

## Описание бота

**Дедушка Вобжак** — Telegram-модератор-бот для чата Бабая. Бот + веб-панель в одном
контейнере. Хостится на Bothost.

### Архитектура
- **Точка входа:** `bot.py` — FastAPI + Aiogram. Режим работы определяется
  автоматически: если `WEBHOOK_URL` задан и вебхук установлен → webhook,
  иначе → Long Polling (фоллбэк).
- **Бот:** `bot_handlers.py` — обработка команд и сообщений (`!mute`, `!warn`,
  `!ban`, `!unmute`, `!unwarn`, `!unban` и т.д.), word/link фильтры, auto-warn/mute/ban
  по порогам, синхронизация админов из TG, логирование Punishment-ов в БД.
- **Веб-панель:** `web_app.py` (FastAPI) + Jinja2-шаблоны (`templates/*.html`).
  Авторизация через cookie-сессии, SU (super-user) + обычные админы.
  Роуты: `/login`, `/dashboard`, `/user/{id}`, `/admin/users`, `/admin/presets`,
  `/api/dashboard`, `/api/search`, и т.д.
- **БД:** SQLite (`db.py`), SQLAlchemy async. 7 моделей:
  `User`, `Moderator`, `Punishment`, `ChatAdmin`, `ChatSettings`, `WebUser`, `Base`.
  Soft-revoke через `is_revoked` флаг на `Punishment`.
- **Окружение (env):** `BOT_TOKEN`, `BOT_ID`, `WEB_PASSWORD`, `SESSION_SECRET`,
  `ADMIN_IDS`, `CHAT_HASHTAGS`, `USER_ID`, `DOMAIN`, `TEMPLATE`, `PORT`,
  `REPORT_CHAT_ID`, `BOTHOST_AGENT_URL`.

### Стек
- Python 3.11+, aiogram 3.x, FastAPI, SQLAlchemy 2.x (async), Jinja2.
- Хостинг: Bothost (Docker-контейнер, agent API на `http://agent:8000`).
- Деплой: замена файлов в Docker image + рестарт контейнера.

## Кодстайл

### Python
- **Импорты:** стандартный порядок — stdlib → сторонние → локальные.
  Группы разделяются пустой строкой.
- **Имена:**
  - Функции/переменные — `snake_case`.
  - Классы — `PascalCase`.
  - Константы — `UPPER_SNAKE_CASE`.
  - Приватные — с префиксом `_` (например, `_sign`, `_make_token`).
- **Логирование:** через модуль `logging`, формат
  `%(asctime)s │ %(name)-24s │ %(levelname)-7s │ %(message)s`.
  Имя логгера — обычно `"shadow_logger"` или имя модуля.
- **Type hints:** применяем везде, где они помогают читаемости.
  `Optional[X]` → `X | None` (Python 3.10+ union syntax).
- **Docstrings:** тройные кавычки `"""`, краткое описание функции в начале,
  детали ниже. Для нетривиальной логики — описание параметров и исключений.
- **Async:** все I/O (БД, Telegram API, HTTP) — async/await.
  Синхронные блокирующие вызовы — только если нет альтернативы (с пометкой).
- **Безопасность:**
  - Секреты — только через `os.getenv`, никогда в коде.
  - Пароли веб-юзеров — PBKDF2-HMAC-SHA256.
  - Сессии — подписанные куки через HMAC.
- **Миграции БД:** в `init_db()` через `PRAGMA table_info` + `ALTER TABLE`.
  Никаких Alembic — простота важнее.
- **Комментарии:** русские, только для нетривиальных мест. Не дублировать код.
  Технические TODO — с пометкой автора и датой.

### HTML / шаблоны
- Jinja2, наследование от `base.html`.
- CSS — inline в `base.html` (CSS-переменные `--sp-*`, `--accent`, и т.д.),
  страницы используют классы из base.
- JS — минимальный, только где необходим (autorefresh, confirm dialogs).
  Никаких тяжёлых фреймворков (React/Vue) — vanilla JS.
- Шаблоны лежат в `templates/` (не в корне проекта!).

### Тесты
- В `scripts/test_v{version}_*.py`, запускаются Python-интерпретатором напрямую.
- Структурные тесты (AST-парсинг исходников) + поведенческие (вызов функций).
- Каждый релиз сопровождается своим набором тестов + регрессионным запуском
  всех предыдущих.

## Версионирование

Формат: `v{MAJOR}.{MINOR}.{PATCH}`, например `v4.7.29`.

### Правила
- **PATCH (последняя цифра):** поднимается с каждым релизом — `v4.7.27 → v4.7.28 → v4.7.29`.
- **PATCH накапливается до 10:** `v4.7.9 → v4.7.10` (не переходим на v4.8.0
  при достижении 10).
- **MINOR bump (вторая цифра):** наступает после PATCH = 9, когда накопилось
  достаточно крупных изменений для minor-релиза. Например:
  - `v4.7.9` → после накопления → `v4.8.0`.
  - Старый roadmap-файл закрывается, создаётся новый `ROADMAP_v4.9.0.md`.
- **MAJOR bump (первая цифра):** зарезервирован для фундаментальных изменений
  (полная переработка архитектуры, смена стека, и т.д.). Не используется
  в обычной разработке.

### Накопительный файл roadmap
- Каждый MINOR-релиз (`v4.X.0`) имеет свой `ROADMAP_v4.X.0.md` файл.
- В нём копятся все идеи, задачи, фидбэк — пока не накопится достаточно для
  нового MINOR-релиза.
- После релиза `v4.X.0` создаётся новый файл `ROADMAP_v4.(X+1).0.md`,
  а старый `ROADMAP_v4.X.0.md` остаётся как историческая справка (не удаляется).
- Текущий активный файл — `ROADMAP_v4.8.0.md`.

### Примеры
- `v4.7.27 → v4.7.28` — patch bump, фикс бот-собственных банов.
- `v4.7.28 → v4.7.29` — patch bump, UX-улучшения веб-панели.
- `v4.7.29 → v4.8.0` — minor bump, накопили веб-разбаны + Bothost API + аудит.
- `v4.8.0 → v4.8.1` — patch bump, фикс после v4.8.0.

## Идеи под оценкой (ожидание решения пользователя)

### 2. Интеграция банов со стрим-платформ (Twitch + GoodGame)
**Источник:** разговор с Бабай (владелец чата), 8 августа.
**Контекст:** Бабай стримит на Twitch и GoodGame. Идея — связать баны на стриме с банами в TG-чате.

#### Главная проблема — синхронизация идентичностей
`Telegram user_id` ≠ `Twitch user_id` ≠ `GG user_id`. Чтобы банить в TG ↔ стрим,
нужно знать соответствие аккаунтов. Варианты:
- **A. Ручная привязка** — пользователь в TG пишет боту `/link twitch <username>`, бот хранит связь. Сложно поддерживать, ник может смениться.
- **B. Ник-онли без привязки** — бот банит по нику из TG-сообщения. Очень хрупко.
- **C. Однонаправленно** — баны **со стрима в TG** (стрим → бот → TG). Не требует привязки, если ники совпадают (часто это так).
- **D. Без автосинхрона** — бот просто **слушает и логирует баны стрима** в веб-панели, модератор сам решает.

#### Оценка сложности

| Сценарий | Сложность | Время (черново) |
|----------|-----------|-----------------|
| Только Twitch, однонаправленно (Twitch → TG), без привязки аккаунтов | Средняя | 2–3 дня |
| Twitch + GG, однонаправленно | Выше среднего | 4–5 дней |
| Двунаправленно (Twitch ↔ TG) с привязкой аккаунтов | Высокая | 1–2 недели |
| Просто логирование банов в веб-панели (без авто-бана в TG) | Низкая–средняя | 1–2 дня |

#### Что нужно для Twitch (Helix API + EventSub)
- Зарегистрировать Twitch-приложение (Client ID + Client Secret).
- OAuth-токен со скоупами `moderator:manage:banned_users` + `channel:moderate`.
- Бот должен быть назначен модератором в канале Бабая.
- Refresh token — access tokens живут ~4 часа.
- Вебхук-эндпоинт (или WebSocket-клиент) для EventSub `channel.ban` / `channel.unban`.
- Rate limits: 800 запросов/мин на токен — для одного канала хватит.

#### Что нужно для GoodGame (WebSocket API)
- Аккаунт бота на GG, привязанный к чату Бабая.
- WebSocket-клиент (`wss://chat.goodgame.ru/chat/websocket`) с heartbeat, reconnect.
- Бот должен быть модератором в чате канала Бабая.
- Баны — через чат-команды модератора (`/ban <nick>`, `/unban`).
- Публичной документации почти нет — придётся реверсить через DevTools.
- WebSocket иногда отваливается, нужен надёжный reconnect.

#### Рекомендация (preliminary)
Начать с **Twitch-логирования (вариант D)** как proof-of-concept:
- Бот слушает EventSub `channel.ban` / `channel.unban` у Бабая.
- Пишет события в БД, показывает в веб-панели отдельной вкладкой «Stream bans».
- Никаких авто-действий в TG — модератор видит и решает сам.

Низкий риск, быстрый выигрыш, дальше можно наращивать. GG добавить отдельной итерацией.

**Статус:** 💡 идея, ждём решения пользователя. Обсудить с Бабай:
- Готов ли он сделать бота модератором на Twitch / GG?
- Какой сценарий нужен (логирование vs авто-бан vs двусторонний)?
- Если авто-бан — готовы ли пользователи привязывать аккаунты (`/link`)?

## Запланированные задачи (взятые в работу на v4.8.0)

### 3. Разбаны в веб-панели — новая вкладка «Active bans»
**Источник:** запрос пользователя, 8 августа.
**Выбранный вариант:** B (отдельная вкладка `/admin/bans` со списком активных банов
по всем чатам + кнопка Unban с optional reason).

#### Что делаем

**Новая страница `/admin/bans`** — таблица всех активных банов по всем чатам:
- Колонки: # / Time (MSK) / User / Chat / Moderator / Reason / [Unban button]
- Фильтры: по чату, по дате, по модератору, по никнейму (search).
- Сортировка по времени (по умолчанию — свежие сверху).
- Pagination, если банов много.

**Кнопка «Unban» в каждой строке:**
- Открывает confirm dialog с полем «Причина (необязательно)».
- Модератор пишет причину (или оставляет пустым) → подтверждает.
- POST `/api/unban` с `{ punishment_id, reason? }`.

**Бэкенд делает:**
1. Помечает исходную `Punishment` (action_type='ban') → `is_revoked = True`,
   `revoked_at = now()`, `revoked_by_mod_id = <web user>`.
2. Вызывает Telegram Bot API `unban_chat_member(chat_id, user_id, only_if_banned=True)`
   — безопасный вызов, не упадёт, если юзер уже разбанен.
3. Создаёт новую `Punishment` запись:
   - `action_type = 'unban'`
   - `reason` = переданный reason (или None)
   - `mod_id` = id веб-модератора (для истории)
   - `is_revoked = False` (разбан сам по себе не «снимается»)
4. Логирует действие модератора (кто, кого, в каком чате, причину).

#### Доступ
- **Кто может разбанивать:** все модераторы + админы + SU
  (уточнить у пользователя при реализации, по умолчанию — все активные веб-юзеры).

#### Что НЕ делаем
- Не делаем batch-unban (пока) — только по одному.
- Не делаем кнопку в карточке пользователя (вариант A) — только в отдельной вкладке.
  Если позже понадобится, добавим отдельной итерацией.
- Не уведомляем пользователя в ЛС о разбане — только молча.
- Не делаем автоматический unmute/unwarn вместе с unban — это разные действия.

#### Сложность и сроки
- **Сложность:** средняя.

### 9. Причесать систему "режимов" чата (alarm / night / sanitary) — рефакторинг на v4.8.0

**Статус:** ✅ реализовано в v4.8.0 (8 августа). Создан модуль `chat_modes.py` с унифицированной логикой snapshot/restore/apply. Дубликаты удалены. Архитектурные инварианты сохранены. Все 436 тестов проходят.
**Детали:** см. `ded-vobzhak-4.8.0_CHANGES.md`.

**Контекст:** после аудита v4.7.30 (см. `AUDIT_v4.7.30_alarm_and_other_commands.md`)
стало ясно, что текущая архитектура "трёх режимов" (alarm, night mode, sanitary
day) разрослась органически и накопила технический долг. Каждый режим имеет свой
snapshot, свой tick, свою логику входа/выхода, свои поля в ChatSettings. Логика
взаимодействия между ними (alarm снимается перед night, alarm снимается перед
sanitary, night пропускается во время sanitary, и т.д.) размазана по коду.

**Что предлагается сделать в v4.8.0:**

1. **Единый "ChatModeManager"** — класс-оркестратор, который знает про все три
   режима и их приоритеты. Вместо трёх отдельных tick'ов — один
   `_chat_mode_tick()`, который для каждого чата решает "какой режим сейчас
   должен быть активен" и применяет/снимает их в правильном порядке.

2. **Унифицированный snapshot** — все три режима используют один и тот же формат
   snapshot прав (JSON с _PERM_FIELDS). Сейчас это уже так, но логика
   восстановления — у каждого своя. Унифицировать через единый
   `_restore_chat_state(cs)` который знает приоритеты:
   - Если sanitary active → sanitary perms
   - Если night active → night perms
   - Если alarm active → alarm perms
   - Иначе → day preset / system default

3. **Единое поле "snapshot прав до всех режимов"** — вместо трёх отдельных
   `*_saved_permissions` полей, одно `chat_default_permissions`, которое
   снимается при входе в ЛЮБОЙ режим и восстанавливается при выходе из ВСЕХ.
   Сложно — нужно мигрировать существующие данные.

4. **Приоритет режимов** — задокументировать явно:
   sanitary > night > alarm > day.
   Если sanitary активен — night и alarm не входят (снимаются если были активны).
   Если night активен — alarm не входит (снимается если был активен).
   Day — это "никакой режим не активен".

5. **Логирование** — единый логер "ChatModeManager" с понятными сообщениями:
   `ChatMode: chat=N entering sanitary (was: alarm, deactivated)`

6. **Тесты** — единый набор тестов для всех комбинаций:
   - alarm + night enter
   - alarm + sanitary enter
   - night + sanitary enter
   - sanitary exit + night enter (auto-transition)
   - и т.д.

**Сложность:** ~2-3 дня. Высокий риск регрессий — нужно прогнать ВСЕ
существующие тесты + добавить новые для комбинаций.

**Альтернатива:** оставить как есть, просто добавить больше тестов на
комбинации. Меньше риск, но технический долг остаётся.

**Решение:** обсудить после v4.7.30 релиза. Если багов в v4.7.30 не найдут —
можно браться за рефакторинг в v4.8.0.

### 10. Модераторский чат (modchat) + keyword-watch + замена word-filter

**Статус:** ✅ реализовано в v4.8.0 (8 августа, обновлено 8 августа — добавлен веб-UI). Создан модуль `modchat.py`, новые поля БД (`mod_chat_id`, `is_mod_chat`), новая таблица `keyword_watch`, 5 новых команд (`!setkeywords`, `!addkeyword`, `!delkeyword`, `!listkeywords`, `!setmodchat`). Все 4 события alarm в modchat + консолидация продлений. Keyword-watch с substring/word-boundary match, rate-limit, multiplexing, exempt модераторов. Day=notify, night=auto-ban для фраз с `ban_in_night_mode=True`. **Веб-UI (добавлен в пересобранной v4.8.0):** кнопка `☆ MOD` на странице `/admin/chats` (взаимоисключение с REPORT — disabled когда чат является report_chat, и наоборот), новая страница `/admin/keywords` (SU-only) с CRUD-управлением фразами (форма добавления + чекбокс `ban_in_night_mode` + кнопки Delete + toggle флага), пункт меню «Keywords» в navbar (SU-only), бейдж `MOD` в списке чатов. Все 436+57 тестов проходят (включая 57 новых тестов для веб-UI).
**Детали:** см. `ded-vobzhak-4.8.0_CHANGES.md`.

**Источник:** запрос пользователя, 8 августа (обсуждение концепции в чате).

**Контекст:** сейчас все оповещения бота сыплются в один репорт-чат
(журнал санкций — мьют/бан/варн с rich-превью). Это мешает: модераторы
хотят отдельный канал для оперативных оповещений, не смешанных с
«большими» репортами о санкциях. Параллельно — текущий word-filter
практически не использовался (боялись ложных срабатываний), его логика
устарела. Решено: объединить обе проблемы в одну фичу.

#### Концепция двух чатов

- **Репорт-чат** (как сейчас) — журнал санкций (mute/ban/warn и снятия).
  Rich-формат с превью сообщения нарушителя. Публичный аудит-лог.
- **Modchat** (новый) — оперативные оповещения для дежурного модератора:
  события режимов чата (alarm on/off) и keyword-watch (упоминания
  заданных фраз). Без медиа-превью, краткий текстовый формат.

**Взаимоисключение ролей:** один и тот же чат не может быть одновременно
репорт-чатом и modchat'ом. В веб-панели при назначении кнопка «MOD»
недоступна для чатов с `is_report_chat=True`, и наоборот. Кнопка
«Disable» снимает текущую роль.

#### Фича A: Alarm-события в modchat

**Что шлём в modchat (4 события):**

1. **`!alarm on`** — «В чате «X» поставлен режим тревоги модератором
   «Y». Длительность: N мин (до HH:MM)».
2. **`!alarm off`** (ручное снятие) — «В чате «X» снят режим тревоги
   модератором «Y»».
3. **Auto-off по таймауту** — «В чате «X» автоматически снят режим
   тревоги. Причина: истёк таймаут (проработал N мин)».
4. **Снятие входом в night mode / sanitary day** — «В чате «X» снят
   режим тревоги. Причина: вход в night mode / sanitary day».

**Консолидация продлений:** если за 60 секунд было несколько
продлений alarm (`!alarm on` когда уже активен), шлём **одно**
консолидированное уведомление:
«🚨 Alarm в чате «X» продлён. Изначально поставил: @ivan. Продления:
@maria (+15 мин, 15:45), @petr (+10 мин, 15:52). Текущее окончание:
16:02». On/off/auto-off/off-by-night — всегда мгновенно, без
консолидации (важные события).

**Формат:** простой текст + emoji-префикс (🚨 alarm). Без rich-блоков —
modchat должен быть быстро читаемым. В отличие от репортов, тут не
нужно превью сообщения нарушителя (его в alarm-событиях нет).

**Fallback:** если modchat не задан — молча игнорируем (DM
модератору остаётся как сейчас, обратная совместимость).

#### Фича B: Keyword-watch (замена word-filter)

**Принцип:** есть список фраз. При упоминании в сообщении — бот шлёт
уведомление в modchat. Не банит, не удаляет, не варнит — только
привлекает внимание дежурного модератора.

**Дневной/ночной режим работы:**
- **День (не активен night mode):** все фразы из списка → только notify
  в modchat. Никаких авто-санкций.
- **Ночь (активен night mode):** фразы с чекбоксом «банить в night mode»
  → применяем действие (ban). Фразы без чекбокса → notify в modchat.
- **Обоснование:** night mode создан для автоматической защиты чата,
  пока модераторы спят. Днём модератор сам решает, что делать с
  упоминанием — бот только привлекает внимание.

**Структура списка (вариант B с упрощением UI):**

Один глобальный список фраз (один на все чаты — правила везде одни).
Каждая запись:
- `phrase` (str) — отслеживаемая фраза.
- `ban_in_night_mode` (bool, default OFF) — применять ли авто-бан
  ночью. Для жёстких фраз (типа «срал в торт детишкам») — ON. Для
  мягких (`@admin`, `помогите`) — OFF.

**Хранение:** новое поле `keyword_watch_list` в `ChatSettings` для
`chat_id=0` (global). JSON-массив объектов `[{phrase, ban_in_night_mode}]`.

**Match logic (минимум ложных срабатываний):**
- Case-insensitive (как в старом word-фильтре).
- **Если фраза содержит пробел** → substring match (фраза «срал в торт
  детишкам» найдёт только эту последовательность, не отдельные слова).
- **Если фраза — одно слово** → word-boundary match (не сработает на
  «замодераторили», если в списке «модератор»). Это убирает ~90%
  ложных срабатываний без regex-настройки.
- **Что матчим:** `message.text` + `message.caption`. Media-only (без
  текста) игнорируем. Редактирования игнорируем. Сообщения от бота
  игнорируем.
- **Exempt:** модераторы/админы/SU пропускаются через существующий
  `_is_admin(session, chat_id, user_id)`. Не триггеримся на их
  сообщения (модератор, пишущий «@admin» — это рабочий кейс, но он
  осознанно пишет, ему не нужна авто-санction).

**Формат уведомления в modchat (rich, как у репортов):**

Rich-блоки для единообразия с репортами:
1. `SectionHeading` — «👀 Ключевое слово в чате «X»»
2. `Divider`
3. `List` — нарушитель (имя кликабельно → `tg://user?id=...`), время
   МСК, сработавшая фраза (или список фраз, если несколько совпадений
   в одном сообщении).
4. `Divider`
5. `Details` — «Текст сообщения» (is_open=False): сворачиваемый блок
   с цитированием текста. По умолчанию скрыт (защита от шок-контента).
6. `Divider`
7. `Footer` — `RichTextUrl(text="Перейти к сообщению →", url=message.link)`.

**Кнопка «Перейти к сообщению»:** `message.link` возвращает URL вида
`https://t.me/c/{internal_id}/{message_id}` (приватные чаты) или
`https://t.me/{username}/{message_id}` (публичные). Telegram-клиент по
тапу открывает оригинал. Модераторы состоят в чате → откроется без
проблем, даже если у чата `has_protected_content=True`.

**Антиспам modchat'а (трёхуровневая защита):**
1. **Rate-limit per (chat_id, keyword):** 60 секунд. Если за минуту
   фраза встретилась 5 раз — шлём **одно** уведомление со счётчиком
   «ещё 4 за последнюю минуту».
2. **Multiplexing:** если в одном сообщении совпало 3 фразы — шлём
   **одно** уведомление со списком «Совпадения: phrase1, phrase3».
   Не 3 разных.
3. **Exempt модераторов/админов/SU** — подтверждено выше.

**Управление списком:**
- **Веб-панель** (основной способ): новая страница в SU-меню
  «Keyword watch list» — таблица фраз с чекбоксом «банить в night
  mode», добавление/удаление/редактирование через UI.
- **Команда `!setkeywords word1,word2,word3`** (SU-only, бэкап):
  задаёт список (полная замена). Для добавления одной фразы —
  `!addkeyword «фраза» [--ban-night]`. Для удаления —
  `!delkeyword «фраза»`. Просмотр — `!listkeywords`.
- Все команды через `!` (в DM также `!`, не `/` — у нас нигде нет
  слэш-команд).

#### Миграция с word-filter

**Решение:** вариант (b) — ручная миграция. Старый `word_filter_list`
**не переносится** автоматически (он и так был пуст — боялись ложных
срабатываний). Администратор заново вносит фразы в новый
`keyword_watch_list` через веб-панель. Старый код word-filter
удаляем полностью (dead code после v4.8.0).

**Что удаляем:**
- `handle_word_filter` и связанные функции в `bot_handlers.py`.
- Поле `word_filter_list` в `ChatSettings` (или оставляем как
  deprecated, не используем — на усмотрение реализации).
- Тесты для старого word-filter (заменяем на тесты keyword-watch).

### 11. Автопополнение сайта правил с веб-панели бота (GitHub sync)

**Статус:** 🔨 запланировано на major-update v4.8.0 (после v4.7.30).
**Источник:** запрос пользователя, 8 августа (после ревью сайта правил
`index.html` из репозитория Degradach на GitHub).
**Зависимости:** зависит от пункта 10 (modchat + keyword-watch) —
использует ту же модель `keyword_watch_list` и тот же UI для
добавления фраз.

**Контекст:** сайт правил чата (`index.html`, single-page) хостится на
GitHub. В нём есть раздел «Бан без предупреждения за» с вложенными
`<details>` блоками, где перечислены конкретные примеры запрещённых
фраз. Сейчас при добавлении новой фразы в word-filter бота модератор
должен отдельно идти на GitHub и редактировать HTML вручную — это
забывается, сайт и список бота расходятся. Хочется: модератор добавляет
фразу через веб-панель бота → бот автоматически коммитит изменение в
GitHub → сайт перестраивается (через GitHub Pages) через 2-5 минут.

**Структура сайта правил (по факту, после ревью `index.html`):**

```html
<!-- ===== SECTION 1: БАН БЕЗ ПРЕДУПРЕЖДЕНИЯ ===== -->
<section class="section--danger">
  <h2>Бан без предупреждения за</h2>
  <ol class="rules-list">
    <li><div class="rule-text">Пропаганда ЛГБТ.</div> ...</li>
    ...
    <li>
      <div class="rule-text">Раковые форсы.</div>
      <details class="rule-details">
        <summary>
          <span class="chevron">›</span>
          <span class="label">Что считается раковыми форсами</span>
        </summary>
        <ul class="rule-details-body">
          <li>Срал в торт</li>
          <li>Фашист</li>
          <li>1984</li>
          <li>Палестинские дети</li>
          <li>Любой форс, который заебал Бабая</li>
        </ul>
      </details>
    </li>
    ...
  </ol>
</section>
```

**Ключевое наблюдение:** структура уже формальная — `<details>` с
конкретным `<summary>` «Что считается раковыми форсами» однозначно
идентифицирует блок. Не надо угадывать, не надо рефакторить сайт.
Бот правит только `<ul class="rule-details-body">` внутри
соответствующего `<details>`, остальной HTML не трогает.

#### Принцип работы

**Добавление фразы (через веб-панель):**

1. Модератор в UI выбирает секцию на сайте (дропдаун: «не публиковать
   на сайте» / «Раковые форсы» / будущие секции) + вводит саму фразу.
2. Бот сохраняет фразу в `keyword_watch_list` (БД) с пометкой
   `rules_section="rakovye_forsy"`.
3. Бот дёргает GitHub API:
   - `GET /repos/{owner}/{repo}/contents/index.html` → получает
     текущий SHA + base64-контент.
   - Декодирует, парсит через `BeautifulSoup`, находит
     `<details>` по тексту `<summary>` «Что считается раковыми
     форсами».
   - Добавляет `<li>{phrase}</li>` перед закрывающим `</ul>`.
   - Кодирует обратно в base64.
   - `PUT /repos/.../contents/index.html` с `{message, content, sha,
     branch}`.
4. При 409 Conflict (кто-то другой только что закоммитил) — один
   retry: снова GET → патч → PUT. Если второй 409 — модератору в
   веб-панель: «кто-то только что изменил список, попробуй ещё раз
   через 30 сек».
5. При успехе — коммит `bot: add banned phrase "{phrase}" (via web
   panel by @{moderator})`. Автор коммита: «Дед Вобжак Bot».
6. GitHub Pages перестраивает сайт за 2-5 минут. Модератору в
   веб-панель: «✅ Фраза добавлена, сайт обновится через ~5 минут».

**Удаление фразы:** обратная операция — находит `<li>` с точным
текстом, убирает, коммитит `bot: remove banned phrase "{phrase}"`.

**Webhook обратно в бота (опционально, рекомендуется):**

- В настройках GitHub repo добавляем Webhook на URL бота
  (`/api/github/webhook`), событие `push`.
- При пуше (от бота, от тебя вручную, от кого угодно) — бот
  скачивает новый `index.html`, парсит все `<details>` блоки,
  сравнивает с `keyword_watch_list` в БД.
- При расхождении — уведомление в modchat: «⚠️ Сайт правил
  обновлён извне. +2 фразы, -1 фраза в секции "Раковые форсы".
  Список в БД синхронизирован.»
- Защита: webhook secret (env var `GITHUB_WEBHOOK_SECRET`) для
  проверки подписи `X-Hub-Signature-256`.

#### Безопасность

- **PAT (Personal Access Token):** fine-grained, scope `contents: write`
  только на этот repo. Срок — 1 год, потом перевыпуск. Хранится в
  env var `GITHUB_RULES_TOKEN`, не в БД, не в логах (маскировать при
  error logging).
- **Commit author:** указываем «Дед Вобжак Bot <noreply@degradach.ru>»
  — чтобы в истории коммитов было видно, что это бот, а не человек.
- **Webhook secret:** env var `GITHUB_WEBHOOK_SECRET`. Без него
  webhook от любого — security risk (можно подделать push event и
  раскоординировать БД бота с сайтом).
- **Логирование:** каждый commit/PR пишем в worklog + в modchat
  (когда будет #10). В случае ошибки коммита — модератору в
  веб-панель + алерт в modchat «⚠️ Не удалось обновить сайт правил:
  {error}».

#### Что НЕ делает бот

- **Не редактирует HTML за пределами `<ul class="rule-details-body">`.**
  Стили, скрипты, easter eggs, другие секции — не трогаем.
- **Не создаёт новые `<details>` блоки.** Если нужна новая секция на
  сайте (например, «Что считается фурри-контентом») — ты сама
  добавляешь HTML вручную, после чего регистрируешь секцию в
  конфиге бота (env var или в БД: `rules_section_id → summary_text`).
- **Не мёржит конфликты автоматически.** При 409 — retry, потом
  ручное вмешательство.

**Риски:**
- **BeautifulSoup может переформатировать HTML** (например,
  нормализовать кавычки, убрать лишние пробелы). Это сломает diff
  при ревью PR'ов и загрязнит историю коммитов. Решение:
  использовать `BeautifulSoup` только для поиска блока, потом
  строковые операции (`str.find`, `str.replace`) для вставки
  `<li>`. Или `lxml` с опцией сохранения formatting.
- **GitHub Pages кэширование** — до 5 минут между коммитом и
  обновлением сайта. Модератору надо сообщать «через ~5 минут», не
  «мгновенно».
- **Race condition при одновременных коммитах** — решается retry
  на 409, но при большой активности (5+ модераторов одновременно)
  может стать узким местом. Для нашего масштаба — маловероятно.
- **PAT в env** — если утечёт, кто-то может коммитить в repo от
  имени бота. Fine-grained token ограничивает blast radius только
  этим repo.
- **HTML-структура сайта может измениться** — если ты сама
  переименуешь `<summary>` «Что считается раковыми форсами» → бот
  не найдёт блок и выдаст ошибку. Решение: при неудачном поиске —
  алерт в modchat «⚠️ Не найдена секция "Раковые форсы" на сайте
  правил. Возможно, HTML был изменён. Проверьте конфигурацию.»

#### Альтернативы (отклонённые)

- **Pull Request вместо прямого коммита в `main`.** Отклонено: ты
  единственный reviewer, и при твоём отсутствии фразы будут висеть
  в PR'ах часами. Прямой коммит + webhook-аудит — быстрее и
  прозрачнее.
- **Отдельный JSON-файл `banned_phrases.json` рядом с `index.html`,
  сайт подгружает через JS.** Отклонено: требует рефакторинга сайта
  (переделывать JS-логику, тестить, что JS работает без сервера на
  GitHub Pages). Текущая HTML-структура уже формальная, бот
  справится.
- **双向 sync (GitHub → БД и БД → GitHub).** Сложно, легко
  раскоординировать. Оставляем однонаправленный (БД → GitHub) +
  webhook только для оповещения о расхождениях (без авто-миграции
  в БД).

#### Открытые вопросы (на момент реализации)

- **BeautifulSoup vs lxml vs string ops для HTML patching?**
  Решить при прототипировании — главная цель минимальный diff.
- **Поддерживать ли несколько секций сразу?** В первой итерации —
  только «Раковые форсы». Если захочешь ещё (например, «Что
  считается фурри-контентом») — регистрируешь в `RulesSection`
  таблице, бот подхватывает автоматически.
- **Логировать ли в modchat каждый коммит?** Думаю да, но с
  уровнем info (не critical). Если будет шумно — добавим
  SU-настройку «тишина для GitHub-коммитов».
- **Нужен ли bot-аккаунт на GitHub (machine user)?** Для тебя —
  нет, твой PAT достаточно. Для команды с несколькими админами —
  стоит завести отдельный GitHub-аккаунт «ded-vobzhak-bot» и
  выдать ему write access к repo.
