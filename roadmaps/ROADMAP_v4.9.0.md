## §1. Рефакторинг + расширение behavioral-тестов (перенесено из v4.8.4)

**Источник:** `ROADMAP_v4.8.x.md`, раздел v4.8.4 (исходная редакция).
**Перенос:** 11 августа 2026, решение пользователя.
**Причина переноса:** v4.8.3 полностью работает в проде как требовалось
(TGS fallback OK, поведенческих багов не найдено), поэтому v4.8.4 стал
чисто баг-фикс патчем. Рефакторинг же логичнее делать в контексте MINOR-цикла
v4.9.0, где будут и другие изменения архитектуры — переезд функции и
расширение тестов можно делать согласованно с изменениями из §2.

### 1.1. Перенос `_alarm_auto_off_tick` из `bot.py` в `bot_handlers.py`

**Источник:** `CODE_AUDIT_v4.8.0.md`, §7.2.1.

**Зачем:** уменьшить coupling между модулями. Сейчас `bot.py` (точка входа,
FastAPI + Aiogram lifespan) содержит бизнес-логику таймеров alarm'а — это
нарушает разделение ответственности. Логика обработчиков должна лежать
в `bot_handlers.py`.

**Что делаем:**
- Перенести функцию `_alarm_auto_off_tick` (и связанные с ней хелперы,
  если есть) из `bot.py` в `bot_handlers.py`.
- Обновить late imports — `_alarm_auto_off_tick` вызывается из lifespan
  в `bot.py`, поэтому потребуется `from bot_handlers import _alarm_auto_off_tick`
  на месте вызова (или вынести в отдельный модуль `timers.py`, если
  логики станет много).
- Проверить, что другие tick'и (`_night_mode_tick`, `_sanitary_day_tick`)
  остались там же где были — их не трогаем в этой задаче (только если
  совещание §2 не принесёт связанных запросов).

**Сложность:** ~0.5 дня.

### 1.2. Расширение behavioral-тестов для веб-панели endpoints

**Источник:** `CODE_AUDIT_v4.8.0.md`, §7.2.3.

**Зачем:** текущие тесты для веб-панели — в основном unit-проверки
(regex, model fields, helper functions). Behavioral-тесты (HTTP-запрос →
ответ → side-effect) покрыты слабо. Это мешает уверенно рефакторить
эндпоинты при добавлении фич из §2.

**Что делаем:**
- Подключить `TestClient` (FastAPI) + in-memory SQLite + `StaticPool`
  для изоляции тестов.
- Покрыть эндпоинты:
  - `/admin/bans` (v4.8.1) — список активных банов, фильтры, pagination.
  - `/admin/keywords` (v4.8.0) — список KeywordWatch, добавление, удаление.
  - `/api/unban` (v4.8.1) — POST с `{ punishment_id, reason? }`,
    side-effect: Telegram API unban_chat_member + новая Punishment запись.
  - Toggle-эндпоинты `/admin/chats/{id}/toggle` — для всех полей
    (CAS, link_filter, night_mode, sanitary, alarm).
- Сценарии покрытия:
  - SU-only access (admin/moderator → 303 redirect).
  - Unauthenticated → 303 redirect to /login.
  - Invalid input (non-numeric chat_id, malformed reason, etc.).
  - Edge cases (empty list, nonexistent ID, concurrent toggle).
  - Telegram API failure → graceful error response.

**Сложность:** ~1 день.

## §2. Запросы модераторов

### 2.1. Самопроверка варнов обычными юзерами

**Источник:** @Gleb (модератор), запрос через бустерский чат, 11 августа 2026.
**Кратко:** обычные пользователи должны иметь возможность самостоятельно
узнать своё текущее количество активных варнов (без просьбы к модератору).

**Контекст проблемы:**

Сейчас `!warns` (см. `bot_handlers.py:4558`) работает только для модераторов:
- Зарезолвить цель можно только через reply на сообщение юзера
  (фильтр `_ModerationCommandFilter` + guard в `handle_group_command`).
- Guard `_is_admin(session, chat_id, from_user.id)` (строка 3730) отсекает
  обычных юзеров — они не могут выполнить команду вовсе.
- Результат отправляется в **DM модератору** (не юзеру, не в чат).
- В бустерском чате юзеры регулярно спрашивают у модераторов «сколько
  у меня варнов?» — это лишний шум для модераторов и задержка для юзера.

**Что показываем юзеру (минимум):**
- Текущее количество активных варнов.
- Пороги автомьюта и автобана (если настроены в `ChatSettings`).

**Что НЕ показываем юзеру (приватность):**
- Причины варнов (могут содержать контент нарушений / цитаты из чата).
- Identity модераторов, выдавших варны.
- Timestamps выдачи.

**Дизайн команды (предлагаемый):**

**A. DM-команда `/mywarns` (primary)** — юзер пишет боту в личку:
- Без аргументов — бот показывает сводку по всем чатам, где у юзера
  есть активные варны (одна строка на чат: `Название чата — N варнов,
  пороги: мьют @ X, бан @ Y`). Если 0 варнов везде — «У вас нет активных
  варнов.»
- С аргументом `/mywarns <chat_id>` — детальный отчёт по конкретному чату.
- Если юзер не может написать боту в ЛС (не запускал /start) — бот
  не сможет ему ответить. Это естественное ограничение Telegram.

**B. Групповая команда `/mywarns` (secondary, для discoverability)** —
юзер пишет команду в группе:
- Бот удаляет сообщение с командой (privacy — не показываем другим,
  что юзер проверяет варны).
- Бот отправляет DM юзеру с его варнами в ЭТОМ чате.
- Если DM невозможен — ephemeral в чат (auto-delete через 30 сек, через
  существующий `_EPHEMERAL_DELETE_SEM`).

**B. Альтернативный синтаксис (для обсуждения):**
- `!mywarns` — если хочется сохранить единый стиль с `!warns`.
- `/mywarns` — если хочется соответствовать Telegram-конвенции
  (обычные юзеры привыкли к слеш-командам).
- Рекомендация: `/mywarns` — слеш-команды для обычных юзеров,
  `!`-префикс для модераторских команд.

**Edge cases:**
- Юзер не имеет варнов в этом чате, но имеет в других — в группе показываем
  «0 варнов в этом чате», в DM — полный список.
- `warn_decay_days > 0` — учитываем decay (только активные варны, как
  в `_count_warns`).
- Чат, где юзер проверяет варны, не имеет `ChatSettings` (новый чат) —
  используем default thresholds из chat_id=0.
- Юзер забанен в чате — всё равно показываем варны (информационно).
- Юзер замучен — аналогично.

**Файлы, затронутые:**
- `bot_handlers.py`:
  - Новый regex `_CMD_MYWARNS = re.compile(r"^/mywarns(?:\s+(\S+))?$",
    re.IGNORECASE)`.
  - Новый handler `cmd_mywarns(message)` — НЕ проходит через
    `_ModerationCommandFilter` (это не модераторская команда).
  - Хелпер `_format_user_warns_summary(session, user_id) -> str` — собирает
    текстовый ответ из всех чатов с активными варнами.
  - Хелпер `_format_user_warns_for_chat(session, user_id, chat_id) -> str`
    — для одного чата (с порогами).
  - В группе — удалить команду + try DM + fallback ephemeral.
  - В DM — ответить напрямую.
- `_HELP_FULL_TEXT` и `_HELP_MODERATOR_TEXT` — упомянуть, что обычные
  юзеры могут использовать `/mywarns` (чтобы модераторы знали и могли
  подсказать).
- `templates/base.html` — changelog v4.9.0 с этой фичей.
- `scripts/test_v490_mywarns.py` (NEW) — тесты:
  - DM без аргументов — сводка по всем чатам.
  - DM с 0 варнов — корректное сообщение.
  - DM с аргументом chat_id — детальный отчёт.
  - DM с невалидным chat_id — graceful error.
  - Группа — команда удаляется, DM отправляется.
  - Группа + DM невозможен — ephemeral в чат с auto-delete.
  - warn_decay учитывается.
  - Приватность: причины и модераторы НЕ показываются.
  - Регулярный юзер (не админ) может выполнить команду.

**Что нужно от пользователя:**
- Подтвердить выбор синтаксиса: `/mywarns` (рекомендация) vs `!mywarns`.
- Подтвердить формат вывода в DM без аргументов:
  - Вариант 1 (краткий): `Чат "X" — 2 варна (мьют @ 3, бан @ 5)`.
  - Вариант 2 (verbose): с названием чата, датой последнего варна и т.д.
- Подтвердить поведение в группе:
  - Удалять команду юзера? (рекомендация: да, privacy).
  - Отправлять DM? (рекомендация: да).
  - Fallback ephemeral в чат если DM невозможен? (рекомендация: да).

**Сложность:** ~1 день (handler + 2 хелпера + тесты + help-текст + edge cases).

**Приоритет:** высокий — простой запрос, частая боль модераторов.

## Описание бота (для справки)

**Дедушка Вобжак** — Telegram-модератор-бот для чата Бабая. Бот + веб-панель
в одном контейнере. Хостится на Bothost.

### Архитектура (актуально после v4.8.x)
- **Точка входа:** `bot.py` — FastAPI + Aiogram.
- **Бот:** `bot_handlers.py` — обработка команд и сообщений.
- **Веб-панель:** `web_app.py` (FastAPI) + Jinja2-шаблоны.
- **БД:** SQLite (`db.py`), SQLAlchemy async.
- **Модели:** `User`, `Moderator`, `Punishment`, `ChatAdmin`, `ChatSettings`,
  `PermissionPreset`, `WebUser`, `KeywordWatch`, `LinkAllowlist`,
  `BannedStickerPack`, `Base` (после v4.8.1 — без `WordFilter`).
- **Модули v4.8.x:** `chat_modes.py` (унификация режимов), `modchat.py`
  (modchat + keyword-watch), `sticker_cache.py` (после v4.8.3, WebP/WebM/TGS
  → BytesIO для rich-отчётов). Модуль `backup.py` для B2-бэкапов — отложен
  в `ROADMAP_v5.0.0.md` (требует B2-секретов от пользователя).

### Стек
- Python 3.11+, aiogram 3.x, FastAPI, SQLAlchemy 2.x (async), Jinja2.
- Хостинг: Bothost (Docker-контейнер, agent API на `http://agent:8000`).

### Кодстайл
См. `ROADMAP_v4.8.0.md` раздел «Кодстайл» — без изменений.

### Версионирование
Формат: `v{MAJOR}.{MINOR}.{PATCH}`. v4.9.0 — MINOR bump после v4.8.5.
После v4.9.0 патчи идут v4.9.1 → v4.9.2 → ... → v4.9.9, потом v4.10.0
(или v5.0.0, если созреют крупные архитектурные задачи — см. `ROADMAP_v5.0.0.md`).
