## ⚠️ АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ — НЕ НАРУШАТЬ

Перенесено из `ROADMAP_v4.8.0.md` (без изменений). Эти правила описывают
существующее и корректно работающее поведение. При любом рефакторинге
в v4.8.x — НЕ СЛОМАЙ их.

### 1. Alarm / Night mode / Sanitary day работают с chat-default permissions, НЕ с per-user overrides

`bot.set_chat_permissions(...)` меняет только общие права чата. Индивидуальные
рестрикты, выданные через `bot.restrict_chat_member(user_id=...)`, Telegram
хранит отдельно — `set_chat_permissions` их НЕ снимает.

- `!alarm on` ставит «только текст» на ВЕСЬ чат. Юзер, персонально замьюченный
  раньше, остаётся замьюченным (права = min(chat, user)).
- `!alarm off` восстанавливает chat-default права. Персональные рестрикты
  НЕ трогаются.
- НЕ вызывай `restrict_chat_member` для всех юзеров при входе/выходе из alarm.
- НЕ снимай per-user мьюты при `!alarm off`.

### 2. Snapshot прав берётся из `chat.permissions`, не из individual members

`bot.get_chat(chat_id).permissions` возвращает chat-default права. Это то,
что нужно для snapshot'а.

### 3. `use_independent_chat_permissions=True` — обязательно для всех `set_chat_permissions`

С v4.7.25. Через `_apply_chat_permissions` (с v4.8.0, `chat_modes.py`) —
параметр проставляется централизованно. **Никогда не убирай.**

### 4. Snapshot хранится в JSON, не в ChatPermissions объекте

`alarm_saved_permissions`, `night_mode_saved_permissions`,
`sanitary_days_saved_permissions` — JSON-строка с 13 полями `_PERM_FIELDS`.
Десериализация через `_restore_permissions()`.

### 5. Порядок tick'ов: alarm → sanitary → night

В `_night_mode_loop` и `_startup_recovery`. Менять нельзя — иначе санитарный
день может войти до alarm'а и сделать snapshot alarm-состояния.

### 6. `_deactivate_alarm` возвращает tuple `(ok, perms_source, slow_source)`

С v4.7.30. Старый код `if await _deactivate_alarm(...)` работает (tuple truthy
если ok=True), но лучше явно распаковывать.

## v4.8.1 — стабилизация + реформа команд + web unban

**Цель:** закрыть долги из v4.8.0 + добить фичу, что была запланирована изначально
(#3 web unban) + реформа команд ban/warn/mute (новые публичные + тихие варианты).

### 1.1. Реформа команд ban/warn/mute

**Источник:** запрос пользователя, 8 августа (после релиза v4.8.0).

#### Контекст

Текущее поведение (v4.8.0):
- `!mute <dur> [reason]` — причина опциональна. После: ephemeral модератору +
  удаление сообщения нарушителя + отчёт в репорт-чат.
- `!warn <reason>` — причина **обязательна** (regex `r"^!warn\s+(.+)$"`). После:
  уведомление нарушителю (ephemeral) + ephemeral модератору + удаление +
  отчёт.
- `!ban <reason>` — причина **обязательна** (regex `r"^!ban\s+(.+)$"`). После:
  отчёт в репорт-чат. Никакого публичного сообщения в чат не публикует.

**Проблемы:**
1. `!ban` не работает без причины — бот просто не регистрирует команду.
2. Команды слишком «тихие» — нарушитель и чат не видят публичной реакции.
3. Нет способа выбрать между «громким» (публичным) и «тихим» (стелс) вариантом.

#### Новое поведение (финальное решение пользователя, 8 августа)

**Правило причины:**
- **Громкие** команды (`!ban`, `!warn`, `!mute`) — причина **ОБЯЗАТЕЛЬНА**.
  Публичное сообщение должно объяснять чату, за что применена санкция.
- **Тихие** команды (`!sban`, `!swarn`, `!smute`) — причина **НЕОБЯЗАТЕЛЬНА**
  (часто уже видна в чате отчётов через пересланное сообщение).

**Формат публичных сообщений** (публикуются в чат, где применили санкцию):

| Команда | Формат |
|---------|--------|
| `!ban <reason>` | `Пользователь "Нарушитель" забанен за "Причина"` |
| `!warn <reason>` | `Пользователь "Нарушитель" получил варн за "Причина"` |
| `!mute <dur> <reason>` | `Пользователь "Нарушитель" замутан за "Причина" на "Продолжительность"` |
| Via-фильтр (авто-мьют) | `Пользователь "Нарушитель" задолбал срать в чат и был замутан на "Продолжительность мута"` |

- Баны бессрочные — продолжительность только для мьютов.
- Via-фильтр — фиксированный текст, причина не пишется.
- **Пересланное сообщение НЕ прикладывается** к публичному сообщению
  (только в репорт-чате остаётся rich-превью, как сейчас).
- Сообщение нарушителя удаляется (как сейчас).

**Ephemeral-сообщения (финальная матрица):**

| Команда | Ephemeral модератору | Ephemeral нарушителю | Публичное в чат |
|---------|---------------------|---------------------|-----------------|
| `!ban` | ❌ убираем | — (нет) | ✅ |
| `!warn` | ❌ убираем | ❌ убираем | ✅ |
| `!mute` | ❌ убираем | — (нет) | ✅ |
| `!sban` | ✅ остаётся | — (нет) | ❌ |
| `!swarn` | ✅ остаётся | ✅ остаётся | ❌ |
| `!smute` | ✅ остаётся | — (нет) | ❌ |

**Исключение:** ephemeral модератору про автодобавление стикерпака при бане
за стикер (`!ban` и `!sban`) — **остаётся**, это техническое уведомление,
не дубликат публичного бана.

**Отчёт в репорт-чат** — падает **ВСЕГДА**, и для громких, и для тихих команд.
Формат rich-превью как сейчас (с пересланным сообщением нарушителя).

**Regex-паттерны (финальные):**

| Команда | Regex | Причина |
|---------|-------|---------|
| `!ban` | `r"^!ban\s+(.+)$"` | обязательна (как сейчас) |
| `!warn` | `r"^!warn\s+(.+)$"` | обязательна (как сейчас) |
| `!mute` | `r"^!mute\s+(\S+)\s+(.+)$"` | обязательна (была опциональна) |
| `!sban` | `r"^!sban(?:\s+(.+))?$"` | необязательна |
| `!swarn` | `r"^!swarn(?:\s+(.+))?$"` | необязательна |
| `!smute` | `r"^!smute\s+(\S+)(?:\s+(.+))?$"` | необязательна (только dur обязательна) |

**Новые тихие команды `!sban`, `!swarn`, `!smute`** — переносят текущий
(v4.8.0) функционал `!ban`/`!warn`/`!mute` 1-в-1:
- Никакого публичного сообщения в чат.
- Ephemeral модератору (как сейчас).
- Для `!swarn` — уведомление нарушителю остаётся (только в этой тихой команде).
- Отчёт в репорт-чат (как сейчас).
- Удаление сообщения нарушителя (как сейчас).

#### Что НЕ меняется

- `!unban`, `!unmute`, `!unwarn`, `!warns`, `!resetwarns` — без изменений.
- Авто-санкции по порогам warn → mute → ban — без изменений, остаются тихими.
- CAS-бан, link-filter бан — без изменений.
- Keyword-watch (notify в modchat, авто-бан ночью) — без изменений.
- Логика `_check_warn_threshold` — без изменений, вызывается из `!warn`/`!swarn`.

#### Решения пользователя (8 августа, финальные)

1. **`!warn` без причины** — ❌ причина обязательна (для всех громких).
2. **Уведомление нарушителю при `!warn`** — ❌ убираем (раз есть публичное).
   При `!swarn` — ✅ остаётся.
3. **`!sban`/`!swarn`/`!smute` без причины** — ✅ разрешено (для всех тихих).
4. **Формат публичных сообщений** — см. таблицу выше.
5. **Кто видит публичное сообщение** — весь чат.

### 1.3. Разбаны в веб-панели — новая вкладка «Active bans» (#3)

**Источник:** `ROADMAP_v4.8.0.md`, задача #3 (детальный дизайн готов).

#### Что делаем

**Новая страница `/admin/bans`** — таблица всех активных банов по всем чатам:
- Колонки: # / Time (MSK) / User / Chat / Moderator / Reason / [Unban button].
- Фильтры: по чату, по дате, по модератору, по никнейму (search).
- Сортировка по времени (по умолчанию — свежие сверху).
- Pagination, если банов много.

**Кнопка «Unban» в каждой строке:**
- Confirm dialog с полем «Причина (необязательно)».
- POST `/api/unban` с `{ punishment_id, reason? }`.

**Бэкенд делает:**
1. Помечает исходную `Punishment` (action_type='ban') → `is_revoked=True`,
   `revoked_at=now()`, `revoked_by_mod_id=<web user>`.
2. Вызывает Telegram Bot API `unban_chat_member(chat_id, user_id, only_if_banned=True)`.
3. Создаёт новую `Punishment` запись:
   - `action_type='unban'`, `reason` = переданный reason (или None),
     `mod_id` = id веб-модератора, `is_revoked=False`.
4. Логирует действие модератора.

#### Доступ

- Кто может разбанивать: все модераторы + админы + SU
  (уточнить при реализации, по умолчанию — все активные веб-юзеры).

#### Что НЕ делаем

### A. Бан по @username / TGID

**3 способа указать цель** (для всех 6 команд: `!ban`, `!sban`, `!warn`,
`!swarn`, `!mute`, `!smute`):

| Способ | Пример | Источник user_id |
|--------|--------|------------------|

**Новые regex:**

| Команда | Regex |

| `!ban` | `r"^!ban\s+(?:(?P<target>@\w+\|\d+)\s+)?(?P<reason>.+)$"` |

| `!mute` | `r"^!mute\s+(?:(?P<target>@\w+\|\d+)\s+)?(?P<dur>\d+[a-zа-я]+)\s+(?P<reason>.+)$"` |

## v4.8.4 — Прогрессивные автомьюты

**Цель:** каждый следующий автомьют длительнее предыдущего. Базовое время
мута берётся из настроек чата, к нему прибавляется штраф — по 1 минуте
за каждый предыдущий автомьют. Счётчик автомьютов не сбрасывается при
очистке варнов (`!resetwarns`), только через `!resetmc` или веб-панель.

Решение пользователя 13 августа 2026 (после уточняющих вопросов).

### Формула

```
mute_duration = base_duration + (automute_count × 60 секунд)
```

Где:
- **`base_duration`** — базовое время мута из настроек чата. Для каждого
  пути автомьюта — свой источник:
  - Порог варнов (`_check_warn_threshold`): `settings.mute_duration_seconds`
  - Via-bot фильтр: `settings.via_bot_mute_minutes × 60`
  - Стикерпак: `pack.mute_duration`
  - Контент-фильтр: `mute_dur` (из настроек фильтра)
- **`automute_count`** — текущее значение счётчика ДО инкремента
  (0 при первом автомьюте, 1 при втором, и т.д.).
- После применения мута счётчик инкрементируется на 1.

**Пример** (base = 5 минут = 300 сек):
| # мута | count ДО | duration | count ПОСЛЕ |
|--------|----------|----------|-------------|
| 1-й    | 0        | 300 сек (5м) | 1 |
| 2-й    | 1        | 360 сек (6м) | 2 |
| 3-й    | 2        | 420 сек (7м) | 3 |
| 11-й   | 10       | 900 сек (15м)| 11 |

### Что делаем

1. **Новая таблица `automute_counters`** в `db.py`.
   - PK: `(chat_id, user_id)` — per-chat per-user.
   - Поле `count` (Integer, default 0).
   - Поле `updated_at` (DateTime).
   - Миграция через `CREATE TABLE IF NOT EXISTS` в `init_db`.

2. **Хелпер-функции** в `bot_handlers.py`:
   - `_get_automute_count(session, chat_id, user_id) → int` — текущее
     значение (0 если записи нет).
   - `_increment_automute_count(session, chat_id, user_id) → int` —
     инкремент, возвращает НОВОЕ значение.
   - `_reset_automute_count(session, chat_id, user_id) → int` — сброс
     в 0, возвращает СТАРОЕ значение.

3. **Модификация 4 путей автомьюта** — каждый получает прогрессивную
   формулу:
   - `_check_warn_threshold` (~L3607) — порог варнов → автомьют.
   - `_check_via_bot_filter` (~L7827) — via-bot rate-limit → мьют.
   - Sticker pack filter mute (~L7712) — забаненный стикерпак → мьют.
   - Content/link filter mute (~L8084) — контент-фильтр → мьют.

   В каждом пути:
   - Считать `count = _get_automute_count(...)` ДО мьюта.
   - `duration = base + count * 60`.
   - Применить `restrict_chat_member` с расширенной длительностью.
   - Инкрементировать счётчик ПОСЛЕ успешного мьюта.
   - В отчёте / ephemeral / публичном сообщении — показывать ТОЛЬКО
     итоговую длительность мута (без разбивки base + penalty).

   **Ручные мьюты (`!mute`, `!smute`) — НЕ затронуты.** Модератор
   указывает длительность явно, счётчик не инкрементируется.

4. **Новая команда `!resetmc`** — сброс счётчика автомьютов.
   - Доступ: только SU/Admin (как `!resetwarns`).
   - Цель: reply НА сообщение нарушителя, ИЛИ `!resetmc @username`,
     ИЛИ `!resetmc <tgid>`.
   - Regex: `^!resetmc(?:\s+(?P<target>@\w+|\d+))?\s*$`
   - Сбрасывает `automute_counters.count` в 0 для (chat_id, target.id).
   - Отправляет DM-подтверждение модератору.
   - Отправляет audit в репорт-чат через `_send_audit_to_report`.
   - Удаляет сообщение с командой.

5. **Сброс через веб-панель** — POST endpoint `/api/reset-automute-count`.
   - Параметры: `chat_id`, `user_id`.
   - Доступ: SU/Admin.
   - Сбрасывает счётчик, возвращает JSON `{ok: true, old_count: N}`.
   - Кнопка в `/admin/bans` или на странице юзера (TBD по месту).

6. **Обновление help** — добавить `!resetmc` в полный help (раздел
   «Снятие наказаний / Прочее»). В moderator-версии НЕ показывать
   (admin-only, как `!resetwarns`). Обновить комментарий в шапке
   `bot_handlers.py`.

7. **Обновление changelog** в `templates/base.html` — запись v4.8.4.

8. **Bump версии** — `web_app.py`: `APP_VERSION = "v4.8.4"`.

### Что НЕ меняется

- Счётчик НЕ сбрасывается при `!resetwarns` (варны и муты — независимые
  счётчики).
- Счётчик НЕ сбрасывается при `!unmute` (снятие мьюта не обнуляет
  историю автомьютов).
- Счётчик растёт бесконечно — нет кэпа, нет автобана после N мутов.

- Счётчик per-chat: муты в чате A не влияют на длительность в чате B.

## v4.8.5 — Идеи от модераторов/админов через бота → GitHub Issues

**Цель:** дать модераторам и админам прямой канал для предложений по
развитию бота — команда `!idea <текст идеи>` в ЛС боту или в
модераторском чате. Идея автоматически попадает как GitHub Issue в
репозиторий проекта (с авто-добавлением в GitHub Project, колонка
«Предложено»). Подключение к проекту настраивается через веб-панель
(вкладка Settings) — без правки env-файлов вручную.

Решение пользователя 14 августа 2026 (перенос старой темы v4.8.5 → v4.8.6).
Ответы на 7 уточняющих вопросов — там же, 14 августа 2026.

### Каналы приёма идей

- **ЛС боту (DM)** — пользователь пишет `!idea <текст>` в личку боту.
- **Модераторский чат (modchat)** — `!idea <текст>` в модераторском чате.

В обычных чатах команда НЕ доступна — только DM и modchat.

### Что должно попасть в GitHub

- **GitHub Issue** в целевом репозитории (создаётся через REST API
  `POST /repos/{owner}/{repo}/issues`).
- **Заголовок Issue** = текст идеи (без префиксов, без description/body —
  только title).
- **Авто-добавление Issue в GitHub Project** через GraphQL Projects v2
  API (`mutation { addProjectV2ItemById ... }`) в колонку «Предложено».
- Метаданные (автор, дата, источник, версия бота) — НЕ на карточке Issue,
  а в логе на стороне бота (таблица `idea_log` в БД). Issue остаётся
  чистым, только заголовок = текст идеи.

### Лимит длины

- **200 символов** на текст идеи.
- Если больше 200 — отказ: «Идея слишком длинная, максимум 200 символов.»
- Краткость — сестра таланта.

### Анти-спам

- **Без cooldown.** Доверяем модераторам/админам, у нас только адекватычи.

### Модерация идей

- **Без модерации.** Идея уходит в GitHub сразу при `!idea`, без
  предварительного одобрения SU.

### Ответ пользователю

После успешного создания Issue:
- **Отправителю** (в DM или modchat): «Спасибо за идею. Передал.»
- **SU в DM** (отдельным сообщением): «Новая идея от `<имя отправившего>`.
  Загляни в проект!» — со ссылкой на созданный Issue в GitHub.

Если создание Issue упало (сетевая ошибка, неверный токен, нет прав):
- **Отправителю**: «Не получилось передать идею, уже чиним.» (или молча —
  уточнить при кодинге).
- **SU в DM**: алерт с текстом ошибки + текстом идеи (чтобы не потерять).

### Кому доступна команда

- **SU / admin / moderator** — могут подавать идеи.
- Обычные юзеры (без WebUser или с `is_active=False`) — игнор, стелс
  сохраняется (как в `/help`).

### Что НЕ делаем в v4.8.5 (переносим в v4.8.6 или позже)

- Голосование за идеи, лайки, рейтинги — позже.
- Авто-перенос из «Предложено» в «В работе» — позже.
- Привязка идей к commit/PR — позже.
- Категории/теги идей — позже.
- Description/body у Issue — никогда (только заголовок).

### Настройка подключения к GitHub Project (через веб-панель)

Вкладка **Settings** в веб-панели — новый раздел «GitHub Projects»:

- **PAT (Personal Access Token)** — вводится в веб-панели, хранится в БД
  в зашифрованном виде (или в отдельной таблице `github_settings`).
  Права PAT: `repo` (для создания Issues) + `project` (для добавления в
  Project v2). Classic или fine-grained — на выбор пользователя.
- **Repo owner** — владелец репозитория (например, `degradach`).
- **Repo name** — название репозитория (например, `ded-vobzhak-ideas`).
- **Project node ID** — ID GitHub Project v2 (получается через GraphQL
  `query { user(login: ...){ projectV2(number: ...){ id } } }` или из URL
  Project через web).
- **Project number** — номер Project в организации/юзере (для удобства).
- **Статус подключения** — кнопка «Проверить» (test connection): создаёт
  тестовый Issue в репозитории и сразу закрывает его, проверяет что PAT
  валиден и права есть. Результат показывается в веб-панели.

Все настройки хранятся в БД (`github_settings` таблица или расширение
существующей `settings`), НЕ в env-файлах. PAT шифруется при записи.

### Зависимости

- **GitHub Personal Access Token (PAT)** — вводится через веб-панель
  (НЕ через env).
- **httpx** (или `aiohttp`) — для запросов к GitHub REST + GraphQL API.
  Вероятно уже есть в зависимостях, проверить.
- **cryptography** (или аналог) — для шифрования PAT в БД. Если уже
  используется — переиспользовать, иначе добавить.

### Логирование идей

В БД добавляется таблица `idea_log`:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Auto-increment |
| `tg_user_id` | BIGINT | TG ID отправителя |
| `tg_username` | TEXT | TG username (на момент отправки) |
| `source` | TEXT | `dm` или `modchat` |
| `idea_text` | TEXT | Текст идеи (до 200 символов) |
| `github_issue_url` | TEXT | URL созданного Issue |
| `github_issue_number` | INTEGER | Номер Issue в репо |
| `created_at` | TIMESTAMP | Время создания |
| `bot_version` | TEXT | Версия бота (например, `v4.8.5`) |

Используется для истории и для алерта SU (имя отправившего берётся
отсюда, а не из GitHub).

Все архивы — в `/home/z/my-project/download/`.

### Git-flow деплоя на Bothost

Деплой на прод идёт через **Git push → auto-redeploy**, а не через ручную
загрузку файлов:

1. Локально вносятся изменения в `/home/z/my-project/v488_work/`.
2. Прогоняется regression: `python /home/z/my-project/scripts/run_v488_regression.py`
   (46 проверок v4.8.7 + v4.8.8, все должны быть зелёными).
3. Собирается zip в `/home/z/my-project/download/ded-vobzhak-{VERSION}.zip`.
4. Пользователь заливает файлы в GitHub-репо `VinylRUS/degramod` (через
   `git push` в `main` или через web-интерфейс GitHub).
5. В Bothost panel — кнопка «Обновить из Git» (или автоматический webhook
   на push, если включён).
6. Bothost клонирует репо, пересобирает Docker-образ (через кастомный
   `Dockerfile` в корне репо), перезапускает контейнер.
7. Проверка: открыть `https://degraban.bothost.tech/` — должна быть страница
   логина. В Telegram отправить `/start` боту — должен ответить.

### Кастомный Dockerfile

В корне репо лежит `Dockerfile` (Bothost подхватывает автоматически, если
в панели стоит галочка «Использовать собственный Dockerfile»):

```dockerfile
FROM python:3.11-slim
WORKDIR /app
RUN mkdir -p /app/data && chmod 777 /app/data
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 3000
CMD ["python", "bot.py"]
```

`requirements.txt` — primary source of truth для зависимостей. Bothost
авто-детектит его и ставит через `pip install -r requirements.txt`.

- Опциональные: `PORT`, `WEB_COOKIE_SECURE`, `WEB_SESSION_TTL_SECONDS`,
