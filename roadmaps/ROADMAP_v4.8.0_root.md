## Описание бота

**Дедушка Вобжак** — Telegram-модератор-бот для чата Бабая. Бот + веб-панель в одном
контейнере. Хостится на Bothost.

### Архитектура
- **Точка входа:** `bot.py` — FastAPI + Aiogram. Режим работы определяется
  автоматически: если `WEBHOOK_URL` задан и вебхук установлен → webhook,
  иначе → Long Polling (фоллбэк).
- **Бот:** `bot_handlers.py` — обработка команд и сообщений (`!mute`, `!warn`,
  `!ban`, `!unmute`, `!unwarn`, `!unban` и т.д.), word/link фильтры, auto-warn/mute/ban
  по порогам, синхронизация админов из TG, логирование Punishment-ов в БД.
- **Веб-панель:** `web_app.py` (FastAPI) + Jinja2-шаблоны (`templates/*.html`).
  Авторизация через cookie-сессии, SU (super-user) + обычные админы.
  Роуты: `/login`, `/dashboard`, `/user/{id}`, `/admin/users`, `/admin/presets`,
  `/api/dashboard`, `/api/search`, и т.д.
- **БД:** SQLite (`db.py`), SQLAlchemy async. 7 моделей:
  `User`, `Moderator`, `Punishment`, `ChatAdmin`, `ChatSettings`, `WebUser`, `Base`.
  Soft-revoke через `is_revoked` флаг на `Punishment`.
- **Окружение (env):** `BOT_TOKEN`, `BOT_ID`, `WEB_PASSWORD`, `SESSION_SECRET`,
  `ADMIN_IDS`, `CHAT_HASHTAGS`, `USER_ID`, `DOMAIN`, `TEMPLATE`, `PORT`,
  `REPORT_CHAT_ID`, `BOTHOST_AGENT_URL`.

### Стек
- Python 3.11+, aiogram 3.x, FastAPI, SQLAlchemy 2.x (async), Jinja2.
- Хостинг: Bothost (Docker-контейнер, agent API на `http://agent:8000`).
- Деплой: замена файлов в Docker image + рестарт контейнера.

## Кодстайл

### Python
- **Импорты:** стандартный порядок — stdlib → сторонние → локальные.
  Группы разделяются пустой строкой.
- **Имена:**
  - Функции/переменные — `snake_case`.
  - Классы — `PascalCase`.
  - Константы — `UPPER_SNAKE_CASE`.
  - Приватные — с префиксом `_` (например, `_sign`, `_make_token`).
- **Логирование:** через модуль `logging`, формат
  `%(asctime)s │ %(name)-24s │ %(levelname)-7s │ %(message)s`.
  Имя логгера — обычно `"shadow_logger"` или имя модуля.
- **Type hints:** применяем везде, где они помогают читаемости.
  `Optional[X]` → `X | None` (Python 3.10+ union syntax).
- **Docstrings:** тройные кавычки `"""`, краткое описание функции в начале,
  детали ниже. Для нетривиальной логики — описание параметров и исключений.
- **Async:** все I/O (БД, Telegram API, HTTP) — async/await.
  Синхронные блокирующие вызовы — только если нет альтернативы (с пометкой).
- **Безопасность:**
  - Секреты — только через `os.getenv`, никогда в коде.
  - Пароли веб-юзеров — PBKDF2-HMAC-SHA256.
  - Сессии — подписанные куки через HMAC.
- **Миграции БД:** в `init_db()` через `PRAGMA table_info` + `ALTER TABLE`.
  Никаких Alembic — простота важнее.
- **Комментарии:** русские, только для нетривиальных мест. Не дублировать код.
  Технические TODO — с пометкой автора и датой.

### HTML / шаблоны
- Jinja2, наследование от `base.html`.
- CSS — inline в `base.html` (CSS-переменные `--sp-*`, `--accent`, и т.д.),
  страницы используют классы из base.
- JS — минимальный, только где необходим (autorefresh, confirm dialogs).
  Никаких тяжёлых фреймворков (React/Vue) — vanilla JS.
- Шаблоны лежат в `templates/` (не в корне проекта!).

### Тесты
- В `scripts/test_v{version}_*.py`, запускаются Python-интерпретатором напрямую.
- Структурные тесты (AST-парсинг исходников) + поведенческие (вызов функций).
- Каждый релиз сопровождается своим набором тестов + регрессионным запуском
  всех предыдущих.

## Версионирование

Формат: `v{MAJOR}.{MINOR}.{PATCH}`, например `v4.7.29`.

### Правила
- **PATCH (последняя цифра):** поднимается с каждым релизом — `v4.7.27 → v4.7.28 → v4.7.29`.
- **PATCH накапливается до 10:** `v4.7.9 → v4.7.10` (не переходим на v4.8.0
  при достижении 10).
- **MINOR bump (вторая цифра):** наступает после PATCH = 9, когда накопилось
  достаточно крупных изменений для minor-релиза. Например:
  - `v4.7.9` → после накопления → `v4.8.0`.
  - Старый roadmap-файл закрывается, создаётся новый `ROADMAP_v4.9.0.md`.
- **MAJOR bump (первая цифра):** зарезервирован для фундаментальных изменений
  (полная переработка архитектуры, смена стека, и т.д.). Не используется
  в обычной разработке.

### Накопительный файл roadmap
- Каждый MINOR-релиз (`v4.X.0`) имеет свой `ROADMAP_v4.X.0.md` файл.
- В нём копятся все идеи, задачи, фидбэк — пока не накопится достаточно для
  нового MINOR-релиза.
- После релиза `v4.X.0` создаётся новый файл `ROADMAP_v4.(X+1).0.md`,
  а старый `ROADMAP_v4.X.0.md` остаётся как историческая справка (не удаляется).
- Текущий активный файл — `ROADMAP_v4.8.0.md`.

### Примеры
- `v4.7.27 → v4.7.28` — patch bump, фикс бот-собственных банов.
- `v4.7.28 → v4.7.29` — patch bump, UX-улучшения веб-панели.
- `v4.7.29 → v4.8.0` — minor bump, накопили веб-разбаны + Bothost API + аудит.
- `v4.8.0 → v4.8.1` — patch bump, фикс после v4.8.0.

## Идеи под оценкой (ожидание решения пользователя)

### 2. Интеграция банов со стрим-платформ (Twitch + GoodGame)
**Источник:** разговор с Бабай (владелец чата), 8 августа.
**Контекст:** Бабай стримит на Twitch и GoodGame. Идея — связать баны на стриме с банами в TG-чате.

#### Главная проблема — синхронизация идентичностей
`Telegram user_id` ≠ `Twitch user_id` ≠ `GG user_id`. Чтобы банить в TG ↔ стрим,
нужно знать соответствие аккаунтов. Варианты:
- **A. Ручная привязка** — пользователь в TG пишет боту `/link twitch <username>`, бот хранит связь. Сложно поддерживать, ник может смениться.
- **B. Ник-онли без привязки** — бот банит по нику из TG-сообщения. Очень хрупко.
- **C. Однонаправленно** — баны **со стрима в TG** (стрим → бот → TG). Не требует привязки, если ники совпадают (часто это так).
- **D. Без автосинхрона** — бот просто **слушает и логирует баны стрима** в веб-панели, модератор сам решает.

#### Оценка сложности

| Сценарий | Сложность | Время (черново) |
|----------|-----------|-----------------|
| Только Twitch, однонаправленно (Twitch → TG), без привязки аккаунтов | Средняя | 2–3 дня |
| Twitch + GG, однонаправленно | Выше среднего | 4–5 дней |
| Двунаправленно (Twitch ↔ TG) с привязкой аккаунтов | Высокая | 1–2 недели |
| Просто логирование банов в веб-панели (без авто-бана в TG) | Низкая–средняя | 1–2 дня |

#### Что нужно для Twitch (Helix API + EventSub)
- Зарегистрировать Twitch-приложение (Client ID + Client Secret).
- OAuth-токен со скоупами `moderator:manage:banned_users` + `channel:moderate`.
- Бот должен быть назначен модератором в канале Бабая.
- Refresh token — access tokens живут ~4 часа.
- Вебхук-эндпоинт (или WebSocket-клиент) для EventSub `channel.ban` / `channel.unban`.
- Rate limits: 800 запросов/мин на токен — для одного канала хватит.

#### Что нужно для GoodGame (WebSocket API)
- Аккаунт бота на GG, привязанный к чату Бабая.
- WebSocket-клиент (`wss://chat.goodgame.ru/chat/websocket`) с heartbeat, reconnect.
- Бот должен быть модератором в чате канала Бабая.
- Баны — через чат-команды модератора (`/ban <nick>`, `/unban`).
- Публичной документации почти нет — придётся реверсить через DevTools.
- WebSocket иногда отваливается, нужен надёжный reconnect.

#### Рекомендация (preliminary)
Начать с **Twitch-логирования (вариант D)** как proof-of-concept:
- Бот слушает EventSub `channel.ban` / `channel.unban` у Бабая.
- Пишет события в БД, показывает в веб-панели отдельной вкладкой «Stream bans».
- Никаких авто-действий в TG — модератор видит и решает сам.

Низкий риск, быстрый выигрыш, дальше можно наращивать. GG добавить отдельной итерацией.

**Статус:** 💡 идея, ждём решения пользователя. Обсудить с Бабай:
- Готов ли он сделать бота модератором на Twitch / GG?
- Какой сценарий нужен (логирование vs авто-бан vs двусторонний)?
- Если авто-бан — готовы ли пользователи привязывать аккаунты (`/link`)?

## Запланированные задачи (взятые в работу на v4.8.0)

### 3. Разбаны в веб-панели — новая вкладка «Active bans»
**Источник:** запрос пользователя, 8 августа.
**Выбранный вариант:** B (отдельная вкладка `/admin/bans` со списком активных банов
по всем чатам + кнопка Unban с optional reason).

#### Что делаем

**Новая страница `/admin/bans`** — таблица всех активных банов по всем чатам:
- Колонки: # / Time (MSK) / User / Chat / Moderator / Reason / [Unban button]
- Фильтры: по чату, по дате, по модератору, по никнейму (search).
- Сортировка по времени (по умолчанию — свежие сверху).
- Pagination, если банов много.

**Кнопка «Unban» в каждой строке:**
- Открывает confirm dialog с полем «Причина (необязательно)».
- Модератор пишет причину (или оставляет пустым) → подтверждает.
- POST `/api/unban` с `{ punishment_id, reason? }`.

**Бэкенд делает:**
1. Помечает исходную `Punishment` (action_type='ban') → `is_revoked = True`,
   `revoked_at = now()`, `revoked_by_mod_id = <web user>`.
2. Вызывает Telegram Bot API `unban_chat_member(chat_id, user_id, only_if_banned=True)`
   — безопасный вызов, не упадёт, если юзер уже разбанен.
3. Создаёт новую `Punishment` запись:
   - `action_type = 'unban'`
   - `reason` = переданный reason (или None)
   - `mod_id` = id веб-модератора (для истории)
   - `is_revoked = False` (разбан сам по себе не «снимается»)
4. Логирует действие модератора (кто, кого, в каком чате, причину).

#### Доступ
- **Кто может разбанивать:** все модераторы + админы + SU
  (уточнить у пользователя при реализации, по умолчанию — все активные веб-юзеры).

#### Что НЕ делаем
- Не делаем batch-unban (пока) — только по одному.
- Не делаем кнопку в карточке пользователя (вариант A) — только в отдельной вкладке.
  Если позже понадобится, добавим отдельной итерацией.
- Не уведомляем пользователя в ЛС о разбане — только молча.
- Не делаем автоматический unmute/unwarn вместе с unban — это разные действия.

#### Сложность и сроки
- **Сложность:** средняя.
- **Оценка:** ~2 дня (новая страница + endpoint + тесты + changelog).

- `templates/admin_bans.html` (NEW) — страница со списком активных банов.

**API endpoints (через `http://agent:8000` из контейнера):**

#### 7.3. TOTP 2FA для SU
**Статус:** 📋 отложено на более поздние версии (после v4.8.0).

**Зачем:** SU-аккаунт — единственный кто может создавать/удалять других админов.
Если SU-пароль утёк — полный контроль над ботом. 2FA закрывает это.

**Когда понадобится:**
- Если SU-пароль когда-либо был скомпрометирован.
- Если появится несколько SU-аккаунтов.
- Если бота будут переносить на другой хостинг / передавать другому владельцу.

**Реализация (когда дойдём):**
- При логине SU → после ввода пароля → запрос TOTP-кода (6 цифр из Google
  Authenticator / Authy / 1Password).
- Секрет хранится в БД (зашифрованный) или в env `SU_TOTP_SECRET`.
- На странице настроек SU — QR-код для привязки к приложению.
- Recovery codes на случай потери телефона.

**Сложность:** ~1 день (`pyotp` + QR-генерация + recovery codes).
**Файлы:** `web_app.py`, `templates/login.html` (новый шаг 2FA), `db.py`
(новые поля у `WebUser` или отдельная таблица `totp_secrets`).

  пользователям не нужно переучиваться.
- SSL-сертификат на свой домен (через Let's Encrypt / Cloudflare).

**Что нужно сделать (черновик, уточнится при реализации):**

1. **DNS-настройка:**
   - В DNS-управлении `degradach.ru` добавить A-запись:
     `mod IN A <IP сервера Bothost>` (узнать у Bothost).
   - Или CNAME-запись: `mod IN CNAME <existing-bothost-domain>`.

2. **На стороне Bothost:**
   - Узнать, поддерживает ли Bothost custom domains (вероятно, через
     переменную окружения `DOMAIN` — она уже есть в env, см. описание бота).
   - Если Bothost использует Traefik (упоминалось в `bot.py`), настроить
     labels или router rule для нового домена.

3. **SSL-сертификат:**
   - Если Bothost автоматически выдаёт Let's Encrypt — ничего делать не нужно.
   - Иначе — настроить Cloudflare в режиме proxy (оранжевое облако) для
     автоматического SSL.

4. **Webhook Telegram:**
   - Если бот работает в webhook-режиме, обновить `WEBHOOK_URL` env на новый
     домен.
   - Перерегистрировать webhook через `setWebhook` API.

5. **Веб-панель:**
   - Проверить, что все ссылки в шаблонах используют относительные пути
     (не хардкод `bothost.ru`).
   - Проверить cookie domain — скорее всего, оставить по умолчанию
     (без явного `domain=`), чтобы куки работали на новом домене.

6. **Telegram Login Widget (если будет добавлен):**
   - В `@BotFather` → Bot Settings → Domain — добавить `mod.degradach.ru`.

7. **exit1.dev monitor (см. пункт 7.2):**
   - Обновить URL монитора на новый домен.

**Что нужно от пользователя:**
- Доступ к DNS-управлению доменом `degradach.ru` (reg.ru / Cloudflare / и т.д.).
- Подтверждение, что Bothost поддерживает custom domains (или готовность
  мигрировать на другой хостинг).
- Решение: использовать Cloudflare как прокси (рекомендуется — бесплатный SSL
  + DDoS-защита) или напрямую.

**Сложность:** низкая, ~0.5 дня (DNS + проверка + перерегистрация webhook).
**Риски:**
- Если Bothost не поддерживает custom domains — придётся либо просить
  поддержку Bothost, либо мигрировать на VPS (это отдельная большая задача).
- Если Telegram webhook был на старом домене — несколько минут простоя при
  переключении (фоллбэк на long polling спасёт).
